# 项目总体计划：智慧充电/停车运营平台（计费业务 + 调度内核 + AI 适配）

> v2.1（2026-09-05 更新：M0 全部完成收口；M1 范围拍板、路线细化）——替代 v1.0「物联网设备平台」方案（已否决）
> 一句话定位：以用户实习认知为抓手（智慧停车/计费/定时升降杆策略），
> 基于现代化改造壳子（reason-faster），构建**充电计费业务 + 调度内核**的运营平台，
> 后期接入 AI 模块（对账差异解释 / 运营数据问答）。

## 一、项目叙事（为什么做这个）

三段可验证的故事线，天然衔接：

1. **实习**：宁波智想科技智慧停车——定时升降杆策略模块（Quartz 调度 + 策略变更）
2. **壳子现代化改造**（已完成）：实习公司脚手架 Boot 2/JDK8 → Boot 3.2/JDK17/jakarta；Shiro 2 → Spring Security 6；MD5/SHA-256 → BCrypt 渐进迁移；测试/CI/文档体系从零建立——全程 9 个 commit 可追溯
3. **本平台**：把 1 的业务认知与 2 的工程资产合流——充电/停车运营（计费）为主干，调度内核（Quartz 升级）为副干线，AI 模块后期接入

选题决策尺子：**用户认知抓手**（业务不陌生 → 能讲透 → 追问扛得住），而非技术炫技。

## 三、业务蓝图（融合逻辑）

```
充电/停车运营平台
├── 设备域：充电桩/地锁/升降杆 台账 + 在线状态（模拟接入起步）
├── 计费域（主干）：计费规则（按时长/峰谷/阶梯）→ 会话（启停状态机）→ 订单（结算）
├── 结算域：支付（对接/模拟）→ 对账 → 差异处理
├── 调度内核（副干线）：壳子 Quartz 升级——misfire 治理/失败重试补偿/告警
│     └── 业务载体：定时策略（升降杆策略 = 实习同构）、账单定时生成/重试
├── 运营支撑：RBAC 复用 + 数据报表
└── AI 模块（后期）：对账差异解释 Agent、运营数据问答 ChatBI（只读 + 建议边界）
```

**融合点说明**：计费订单是业务主干（算钱 = 状态机/并发/事务的天然考场）；调度内核与实习经验同构（策略定时变更），升级版补上壳子缺失的重试/告警治理；AI 模块与既有 club-agent 经验衔接（Java 业务 + Python Agent 混合）。

## 四、迭代路线（块划分，从最简可跑开始）

按用户叙事：**先跑通业务流程（正确性优先），安全/效率/高并发后置（增强级）**——
但并发正确性（状态机/事务/唯一约束）属第一刀地基，不做后置。
块循环机制贯穿：讨论设计 → 实现 → 讲解 → 消化 → 沉淀文档 → 自动提交。

### 架构决策（2026-09-04 定案）：模块化单体 + 限界上下文 + 设备模拟独立服务

用户想象（已纳入）：停车与充电**分属不同管理方**，充电可给予停车优惠（如充电免停 1 小时）；
存在**设备模拟服务**（订单开始通过 HTTP 传输控制设备）。

关键重构：**把「多管理方」与「微服务」解耦**——

- 业务主体 = 模块化单体：同一进程内划分 parking/charging 两个限界上下文（清晰领域包），
  跨域只走显式接口 + 领域事件（charging 完成 → 事件 → parking 应用优惠）；
  一致性问题（事件丢/重放/对账）在单体内完整上演——业务复杂度与面试密度不减，服务器/运维负担不加
- 设备模拟 = **独立小服务**（父 pom `reason-device-sim` module 同仓库形态，内外边界先拆）：设备属「外部世界」，真实中不归业务方运维；
  模拟器独立后业务进程干净，将来升级 MQTT/真实协议零改动
- 演进式拆分触发条件（业务服务拆开）：部署独立演进需求 / 压测证明单体成为瓶颈——
  到时把领域事件走 HTTP/MQ 即拆分动作本身（边界已就位）
- 资源约束：云服务器 4C4G（可用 3.0Gi），多 Java 服务 + 中间件物理拥挤——模块化单体是资源现实下的企业合理路径（monolith-first 行业共识，非简化）
