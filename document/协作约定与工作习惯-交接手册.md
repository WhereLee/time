# 协作约定与工作习惯（Agent 交接手册）

> 受众：接手本工作区的新 agent。本档汇总"怎么与用户协作"的约定——与《Git 与 CI 交接手册》（怎么操作仓库）互补，**建议先读本档、再读那份**。
> 基线：2026-09-11。习惯会演进——本文档未覆盖处不要臆断，直接对话询问；与用户当次明确表态冲突时，**以用户当次表态为准**。
> 项目性质：用户的求职作品集工程，但用户要求**按真实生产标准完整实现**——"面试项目"不是简化理由，而是质量要求更高的理由（见 §二.2）。

## 一、沟通方式

1. **语言**：中文交流（代码/标识符/技术名词保持原文）。
2. **要讨论伙伴，不要迎合**：用户明确要求像同事一样讨论——可以质疑他的方案、可以指出他理解有误、可以给不同技术意见；禁止只顺着说。不确定时承认不确定，摆事实讲技术。
3. **不要"面试话术"**：讨论就事论事讲技术本身，不要主动教"面试怎么说/面试官视角"类内容；用户主动问面试相关时再谈。
4. **不要选项式提问**：禁用 AskUserQuestion 类"选择题"询问（用户反感）。有疑问或需要澄清，直接用对话文字说明，用户会自己回答。
5. **汇报风格**：数据密度高（表格/数字/证据路径）；**如实声明**（"未做/未验证/推导值"必须与"实测值"分开写清）；不夸大、不美化。

## 二、动手与决策约定

1. **动手前先确认**：实质性操作（建文件、改代码、跑会改变状态的命令）之前，先用对话说清"要做什么、怎么做"，用户确认后再执行。用户已明确授权范围内的连续执行不必每步再问；**发现授权范围外的问题 → 先汇报再动**。
2. **严禁擅自简化**：不得以"项目规模小 / 面试项目 / 够用就行 / 性价比低"为由简化功能或设计。
   - 通用框架、工程基建：按企业级标准；
   - 业务流程：可灵活，但必须说清"简化与不简化的差别"，**由用户拍板**；
   - 编码受阻被迫简化：记录在案，结束后向用户阐明。
3. **决策权在用户**：AI 给方案、给建议、给证据，拍板永远是用户。范围取舍、"要不要做某功能"类问题不要默默替用户决定。
4. **默认需求都要做**：用户提出的需求默认成立；排优先级用"先后"而非"做不做"。

## 三、工作流程习惯（块循环）

每个工作块（功能/修复/治理）的固定节奏——用户多年的工作方式，按此节奏协作：

1. 讨论方案（对话确认）→ 2. 实施（小块推进）→ 3. 验证（单测 + 剧本/压测，证据落档）→ 4. 文档沉淀（块记录 + 按需 pitfalls/fixes/knowledge）→ 5. 本地全量验证绿后自动提交推送 → 6. CI 监视至绿

要点：

- **验证前置**：push 前本地必须 `mvn -pl reason-main clean test` 全绿。**clean 必须**——本项目有"增量编译误判（Nothing to compile 却跑旧类）"的多次历史。
- **攒批推送**：代码与其测试**同批完成**才 push；纯文档可攒批——避免中间态触发多次 CI、红链噪音淹没真问题。
- **如实收口**：块结束写块记录（做了什么/取舍/验证/遗留）；未完成项明确标注"待环境/待授权"，不留含糊。

## 四、环境与工具（本地 Windows）

1. **PowerShell 5.1**：不支持 `&&`（用 `;`）；含引号嵌套/变量/多语句/中文的命令**写成脚本文件再执行**（内联转义多次翻车，别试）；`.ps1`/`.bat` 文件**内容全英文**（GBK 解码陷阱）；写文件显式 UTF-8（`[System.IO.File]::WriteAllText`，勿用 `Set-Content`/`Out-File` 默认编码）；字符串替换用 `.Replace()`（`-replace` 是正则，有 `$()<>` 陷阱）。
2. **全栈本地在跑**：MySQL 3306 / Redis 6379 / RocketMQ 9876+10911+8081 / 平台 8200 / sim 8300。平台重启：`mvn -pl reason-main spring-boot:run -Dspring-boot.run.profiles=dev`（先编译再启动，全新编译约 1 分钟；health 检查 `/api/actuator/health`；sim 会自动恢复心跳上报）。
3. **日志读取**：logback 持有日志句柄，普通 `ReadLines` 会 IOException——需以 `FileShare.ReadWrite` 共享打开。
4. **工具失败先验证**：文件写入类工具报 "unknown" 可能是"**报败实成**"的幽灵行为——先检查实际状态，再决定重试/修。
5. **JMeter**：`C:\Users\lrs\Desktop\tools\apache-jmeter-5.6.3`（剧本在 `scripts/verify/batch7-8/`，密钥经 CSV 注入、仓库零明文）。

## 五、文档组织习惯

- **一问题一文件**（`document/` 下）：block-records（批次记录）/ pitfalls（坑位）/ fixes（修复档）/ knowledge（技术知识）/ plans（方案）/ roadmap（待办）——**禁止堆大文档**。
- **证据链入仓**：`scripts/verify/batchN/`（剧本 + 统计输出 `_out.txt`）；大体积原始文件（jtl 等）归档 `diag-archive/`（工作区根，不入 git）。
- 文档里"实测值"与"推导值"分开写；边界与未做项显式声明。
- **密钥/口令零明文**——代码、文档、提交、聊天、记忆，全部不行；临时密钥文件（如设备密钥导出）用后即删。

## 六、红线（必须遵守）

1. **密钥零明文**（含临时文件及时清理）。
2. **悬置队列不擅自 push**：仓库处于"用户已知的待推/待定状态"时，先只本地 commit，推送等用户指示（push 会连带推送整个队列）——见《Git 与 CI 交接手册》§二.5。
3. **归档优于删除**：删除有风险的产物优先"移动/归档"（diag-archive 模式，"移动非删除"）；破坏性操作（force push / 删数据 / 改服务配置）必须先确认。
4. **云服务器**：连接方式见工作区根《服务器连接文档.md》（不入 git）；云上操作已授权，但破坏性操作仍需先确认。
