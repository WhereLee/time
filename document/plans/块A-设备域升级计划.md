# A 块计划：设备域升级（商超停车场模拟资产 + 设备在线体系）

> 状态：✅ 设计定稿（2026-09-06，六条决策按推荐全部采纳），开工 A-1
> 关联：块序列 A-G（用户放行按序开发）；讨论记录 v4（单一运营方/自由停放+位检/占位与券规则已定稿，本块不触碰业务规则）
> 定位：纯结构性块——造"设备与事件通道"，会话状态机升级归 B 块

## 1. 目标与验收标准（A done 定义）

**目标**：把"3 车位演示"设备域升级为"300 车位商超停车场"模拟形态：车位/桩/闸机/位检全量资产化，设备统一在线体系（心跳/离线判定/管理端可见），sim 支持批量心跳与故障注入，手动抬杆形成"管理端指令 → sim 执行 → 留痕"闭环。

验收：
1. DB 资产可重复部署：300 车位（普通区 + 充电专区）+ 30 桩 + 设备台账数据，脚本幂等两遍验证
2. sim 以配置化方式生成 300+ 设备清单（非手写），心跳批量聚合上报（10s），单设备事件通道不变
3. main 记录设备在线状态：心跳更新、超时（30s）判离线、管理端可分页查看（含类型/绑定对象/在线态）
4. 手动抬杆闭环：管理端操作（带操作人/原因/车牌录入）→ 指令下发 → sim 执行回执 → 留痕可查
5. 故障注入：sim 可将任意设备置离线/恢复，main 在线态随之变化（演示"设备离线影响"）
6. 单测全绿 + CI 绿（08 资产脚本挂载容器验证幂等）

## 2. 范围边界

**做**：设备在线表 DDL 与实体；08 资产脚本（300 车位 + 30 桩 + 设备台账数据，删旧建新演示资产语义）；sim 规模化改造（批量生成/聚合心跳/闸机与位检设备类型/故障注入）；main 心跳接收与在线判定；管理端设备面（列表/在线/手动抬杆指令）；CI/部署脚本配套。

**不做（B 块）**：停车会话状态机升级（待绑定态/离位态）、位检绑定语义、入场/出场事件链改造、挪车/手动放行后会话处置——本块只把设备与事件通道、指令留痕备好。

## 3. 设计决策定稿（2026-09-06 用户拍板"按推荐走"）

1. **分离业务台账与在线台账**：新建统一设备在线表（device_no/类型[入口闸机/出口闸机/位检/充电桩]/绑定对象[出入口/车位/桩]/在线态/最后心跳）；charging_pile 业务台账不动，桩的在线态也入此表（同 device_no）
2. **心跳批量聚合上报**：sim 每 10s 一次批量上报全部设备状态（真实"网关聚合"语义），事件单发通道不变；main 超时 30s 判离线
3. **资产布局**：300 车位 = A/B 普通区（270）+ C 充电区（30 绑桩 10%）；预置 SQL 生成器产出不手写
4. **出入口**：3 个出入口（东/南/西）× 入口/出口闸机 = 6 台；位检每车位 1 台（300）
5. **手动抬杆**：本块做设备控制闭环（指令+回执+留痕：操作人/原因/车牌人工录入）；异常会话处置语义留给 B 块
6. **故障注入**：sim 支持任意设备置离线/恢复（模拟接口，成本低）

## 5. 影响面与风险

- db/07（B-001~003 + PILE-001~003）与 08 资产重设的关系：08 采用"删旧建新"演示资产语义（清 07/08 预置区段 → 全量重建），07 保留历史可执行但云上部署改用 08 全量资产；既有 IT 用自建 IT- 前缀车位不受影响
