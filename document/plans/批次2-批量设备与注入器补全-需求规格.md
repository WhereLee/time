## 1. 背景与现状基线（已实证，勿破坏）

- **sim 侧设备清单硬编 2 台**：`reason-barrier-sim` 的 `application.yml` 显式 `sim.devices`（BARRIER-E-01/BARRIER-W-02 + 各自 `${ENV}` 密钥），`BarrierRegistry.init()` 遍历装配，进程级单 `bootId`（重启=代际重置语义）
- **心跳已并行化（P5 已落地）**：`HeartbeatReporter` 每设备独立 `scheduleAtFixedRate` + 共享有界线程池（`sim.heartbeat-threads=8` 默认）+ JDK HttpClient 连接复用；平台判活=Redis online key TTL（30s），心跳周期 10s
- **事件双写（阶段2）**：`DualWriteEventReporter` → HTTP（单发送线程保序 + 退避重试）+ MQ（broker 故障缓冲重试）；平台双入口（HTTP controller + MQ consumer）共用序守卫/销账/告警编排，业务幂等天然吸收双路径
- **注入器现状（0.1-0.8 最小集已具备）**：`NetworkCondition` + `POST /sim/network`——上行断（blockUpstream）/事件独立断（blockEvents）/下行断（blockDownstream）/丢下一次事件（dropNextEvent，一次性）/心跳延迟（heartbeatDelayMillis）。**全部只作用于 HTTP 事件/心跳通道**；MQ 通道故障剧本=真实停起 broker（MqEventReporter 注释已声明），不叠加应用层注入
- **平台监控扫描**：`DeviceMonitorServiceImpl.scanOffline()` 全表查"接入过"设备后**逐台 `hasKey`**（类内注释已注明"生产海量设备用 pipeline 批量判定（此处注明不实现）"）；MonitorTask cron 30s（barrierMonitorTask，schedule_job 固定 job_id=201）
- **告警关闭路径写放大**：心跳处理末端无条件调 `markOnlineRecovered(deviceNo)` → 每次心跳对 device_alarm 发一次 UPDATE（无未处理 OFFLINE 时 rows=0 但 UPDATE 已发出）；事件路径 `markRecovered` 同理但事件低频
- **告警 raise DB 兜底查重**：SETNX 占位成功后 `selectCount(device_no, alarm_type, alarm_createtime > now-窗口)`；现索引 `idx_device_handled(device_no, alarm_handled)` 与 `idx_type_time(alarm_type, alarm_createtime)` 均不覆盖该条件组合
- **密钥一致性现状**：平台登记 `saveRecord` 内部 `UUID.randomUUID()` 生成 32hex secret，**不回显、登记接口不接受外部指定**；sim 侧密钥靠人工从 DB 取同值配置（联调同步语义）
- **批次1 可观测能力已就位**：traceId 全链贯穿 + sim 文件日志 + 结构化日志（事件入口 info/心跳 debug/拒绝 warn）——本批次剧本取证直接复用

## 3. 架构决策（全部定稿，出处见红线/终稿规格）

| 决策 | 定稿 | 理由（简） |
|---|---|---|
| B1 生成式与显式清单关系 | **二选一**：`sim.device-count=0`（默认）→ 维持显式 `devices` 语义零回归；`>0` → 设备清单完全由生成式构成（显式列表忽略，类注释写明）。日常 yml 不写该键；50 台剧本用新 profile `application-batch.yml` | 语义无歧义（count=总数而非增量），日常形态零改动 |
| B2 生成式命名 | deviceNo=`{deviceNoPrefix}{序号}`（前缀默认 `BARRIER-B-`，序号 1 起 %02d → BARRIER-B-01…50）；name=`{deviceNamePrefix}{序号}`（名称前缀默认 `批量杆-`）；bootId 沿用进程级单值（见范围外） | 与平台登记/剧本断言可编程对齐 |
| B3 密钥一致性 | sim 从**本地密钥文件**加载（`sim.secret-file`，每行 `deviceNo=32hex`，`#` 注释，路径 gitignore）；平台 `save` 支持**可选 `deviceSecret` 入参**（空=现随机生成；非空=校验 `^[0-9a-f]{32}$` 后采用）——批量登记脚本一次产出两份：sim 密钥文件 + 平台 save 请求体 | 0.5 语义=per-device 强随机密钥、仓库零明文、双侧同值。50 台不可能 50 个环境变量；文件注入=设备"出厂烧录"语义；平台接受显式密钥=登记脚本唯一闭环路径（现状 save 不回显密钥，sim 无通道拿到同值） |
| B4 密钥文件缺失语义 | secret-file 配置了但**文件不存在 → 启动 fail-fast**（配置错位立即暴露）；文件存在但某台设备缺行 → 该台 secret 置空，走现有 fail-safe 路径（上报取消 + error 日志，与显式列表缺密钥同语义） | 50 台全静默不上报=难发现事故；启动期显式失败成本最低 |
| B5 markOnlineRecovered 门控 | 新增 Redis 标记 key `barrier:alarm-open:{deviceNo}:{typeCode}`（无 TTL，显式生命周期）：**raise 落库成功且 type=OFFLINE 时 SET**；**markOnlineRecovered 先 GETDEL（原子取删），命中才 UPDATE**；GETDEL 抛异常（Redis 故障）→ 记 warn 并**按命中处理**（执行 UPDATE，防漏关）。只作用于 OFFLINE 关闭路径；`markRecovered`（事件路径，低频）不加门控 | 心跳洪峰下 OFFLINE 关闭路径零空 UPDATE（正常设备零 DB 写）；Redis 故障保底不丢自动关闭（退化=现状行为） |
| B6 scanOffline 批量判定 | 一次 selectList 后构造全部 online key → `executePipelined` 批量 hasKey → 离线集循环 raise（raise 内部逻辑不变） | 注释承诺兑现；50 台量级单轮毫秒级 |
| B7 告警查重索引 | 新增索引 `(device_no, alarm_type, alarm_createtime)`，增量脚本 `db/06-barrier-batch-scale.sql`（05 风格幂等：INFORMATION_SCHEMA.STATISTICS 判存在再 ALTER） | raise DB 兜底查重条件全命中该索引；EXPLAIN 验收 |
| B8 注入器扩展落点 | 全部落在 HTTP 事件通道发送路径（HttpEventReporter），NetworkCondition 增三个开关：`eventDelayMillis`（持续生效，0 关）/ `replayNextEvent`（一次性：下一条**成功送达**的事件同报文重发 1 次，失败不消费布防）/ `reorderNextDeviceNo`（一次性：该设备下两条事件集齐后按 eventSeq 降序发送；仅来 1 条超时 5s 原序放行） | 与注入器哲学一致（MQ 通道不叠加）；重放=审计幂等验证需"真送达后再重发"；乱序跨设备无业务意义（序守卫 per-device），窗口固定 2 条=实现最小、剧本可控（e1/e2 倒序） |
| B9 心跳线程数 | `sim.heartbeat-threads` 默认 8→**16** | 50 台节拍 5rps + 延迟注入余量（50 台 × 2s 延迟 / 10s 节拍 ≈ 10 并发需求 <16）；池化常驻成本可忽略；2 台日常场景无感 |

### B. 平台登记显式密钥 + 密钥一致性闭环（reason-main）

**B1 `DeviceRecordForm` 增可选字段 `deviceSecret`**（@Schema 注明：批量联调剧本使用——登记脚本产出的 32hex 强随机值，仓库零明文；日常登记不传）

### C. 平台量级适配（reason-main + db）

**C1 `DeviceMonitorServiceImpl.scanOffline()`**：改造为"一次 selectList → 构造全部 key → executePipelined 批量 exists → 遍历结果收集离线集 → 循环 raise"；方法内注释同步（删除"此处注明不实现"）。启动宽限期逻辑与 raise 内容不变；pipeline 异常保持现状冒泡（任务失败进 schedule_job_log，阶段1 T12 修复后日志已带根因）

**C2 门控（B5）**：
- `BarrierRedisKeys` 增 `ALARM_OPEN_PREFIX = "barrier:alarm-open:"`（key=`{prefix}{deviceNo}:{typeCode}`；类注释补"标记存在=该设备有未处理 OFFLINE 待恢复路径自动关闭"）
- `DeviceAlarmServiceImpl.raise`：落库成功后若 type==OFFLINE → SET 标记（value="1"，无 TTL）
- `DeviceAlarmServiceImpl.markOnlineRecovered`：GETDEL 标记 → 未命中 return 0（零 DB 写）；命中或 GETDEL 抛异常（warn + 降级）→ 执行现 UPDATE 逻辑

- 类注释更新（去重键/标记键职责分离）

**C3 索引（B7）**：新建 `db/06-barrier-batch-scale.sql`（头注释仿 05 格式：批次2 量级适配；幂等：STATISTICS 查 `idx_device_no_type_time` 不存在才 ALTER TABLE device_alarm ADD KEY）

### D. 注入器补全（reason-barrier-sim，仅 HTTP 事件通道）

**D1 `NetworkCondition` 增三开关**（风格同现有成员：volatile/AtomicBoolean/注释）：
- `eventDelayMillis`（volatile long=0）+ setter（warn 日志仿 heartbeatDelayMillis）
- `replayNextEvent`（AtomicBoolean）+ `consumeReplay()`（CAS 取）——布防与消费分离：消费点=发送成功之后
- `reorderNextDeviceNo`（volatile String=null）+ setter

**D2 `HttpEventReporter` 发送路径接入**（单发送线程内实现，天然无并发问题）：
- 发送前：eventDelayMillis>0 → sleep（记 warn `[网络剧本] 事件被延迟 Xms`）
- 乱序窗口：目标设备 == reorderNextDeviceNo 时，该设备事件进窗口缓冲（最多 2 条；缓冲期间其他设备事件照常发送）；集齐 2 条 → 按 eventSeq 降序逐条执行发送；只来 1 条 → 5s 超时后原序放行（一次性开关随窗口完成自动复位）
- 重放：单条发送成功（含重试成功）后消费 replay 布防 → 命中则**同报文（同 body/同签名头/同 traceId）再发 1 次**（重发失败按普通发送失败处理：走一次退避，不递归重放）
- 失败（重试耗尽丢弃）不消费 replay 布防（不放大故障，注释写明）

**D3 `SimController /sim/network`**：body 增 `eventDelayMillis`（long，0 关）/ `replayNextEvent`（bool）/ `reorderDeviceNo`（String）；回显 msg 同步（仿现格式）；注释更新注入端点清单

**G2 事件洪峰（主 DoD 后半）**：
1. 对 50 台批量下发动作指令（骨架硬性：10 台一组并行，每台 OPEN→等台账翻转→CLOSE→等翻转，共 2 轮=100 条指令/≥200 事件；指令间隔 > moveMillis(3s)+余量，避免 MOVING 被拒；命令细节可在实施记录补全，骨架与断言不得缩水）
2. 断言：全部流水终态（ARRIVED，无 PENDING/SEND_FAILED 非预期）；台账终态=每台末次指令目标态；告警表=剧本预期集合（零非预期）；MonitorTask 最近轮次 schedule_job_log.log_duration < 30s（远小于周期）；DB 无慢查询现象
3. 证据：流水终态 SQL 计数、告警列表、schedule_job_log 抽样、耗时统计

**G3 注入器三连（功能验收）**：
1. **乱序**：对单台布防 reorder → 平台连发 OPEN/CLOSE（间隔完成）→ 预期：e2 先达受理、e1 迟到被平台序守卫拒（日志"事件序守卫拒绝(同代际旧序…)"）；MonitorTask 轮询收敛后流水终态=CLOSE 指令 ARRIVED、旧 OPEN 指令按 0.2 代际裁决收敛为 SUPERSEDED（轮询 ≤90s）；台账=末指令目标态（乱序不污染终态=真事件不误伤）；无 DEVICE_FAULT 等非预期告警。若实测 seq1 收敛为 RETRY_EXCEEDED（与代际裁决预期不符）→ 如实记录为阻塞项移交主 agent 判定，**不得自行修改仲裁逻辑**
2. **重放**：布防 replayNextEvent → 单次动作 → 平台同 eventSeq 报文二至：一次受理、一次序守卫拒绝；流水 ARRIVED 只销一次（无重复记账）；台账正确
3. **延迟标定**：eventDelayMillis=2000（<grace 3s）→ 动作 → 无心跳校正干预，事件正常受理闭环；eventDelayMillis=5000（>grace）→ 动作 → 事件延迟到达仍被受理（序守卫不误伤真事件），若心跳相位先达触发一次 STATE_MISMATCH 信息告警=已标定行为（P7 结论留档：事件延迟应 <grace，标定边界 3s 不变，参数调整属阻塞项）
4. 证据：sim 日志（乱序放行/重放/延迟 warn 行）、平台序守卫拒绝日志、流水/告警终态查询
