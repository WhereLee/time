# 升降杆样例——红队评估与成长升级路线

> 版本：v3.0（v2.2 基础上：部署物理形态回退单机——平台与虚拟设备同机部署；**评估标尺不变：虚拟设备永远不算内网**，应用层机制按异地不可信设备设计，网络故障场景由应用层注入器制造验证）
> 日期：2026-09-08
> 方法：红队驱动的健壮性工程。先当坏蛋系统化攻击（找洞、写剧本），修复与技术引入（MQ/可观测/负载模拟等）由事故剧本与目标取舍逼出，不为叙述而升级。
> 审计资产：git HEAD=`ef1373e`。三个子 agent 并行审计（平台设备域+安全链 / 模拟器+双进程契约 / 基础设施·配置·可观测·调度治理），本人复核决策级代码。三份多角度审查（红队完备性 / 架构决策严谨性 / 样例价值与落地性）已并入本版。

## 0. 红线（所有决策的裁决准则）

> **R1 部署巧合 ≠ 架构理由；虚拟设备永远不算内网。** 用户定稿（2026-09-08）：**物理部署形态回退单机**（平台与虚拟设备同机——开发/演示便利），但**评估与设计标尺不变：虚拟设备 = 异地不可信设备**。禁止以"同机/本机/内网"为由削弱或下调任何应用层机制（鉴权/防重放/幂等/重试/超时/对账/故障显式化）——历史教训：曾以"本地在内网"为由提议删 X-Device-Token 被否；曾先验堆 MQ 被否。网络故障场景（延迟/丢包/乱序/单向断）由**应用层注入器**制造验证（本地可控、可进 CI），不依赖真实跨网部署。
> **R2 技术押注必须经得起"量级预算 + 目标取舍"复核。** 既不许拿当前业务量（5rps）砍架构（样例=真实系统压缩版，量由模拟器制造），也不许无剧本引入中间件（先验堆砌）。每条理由必须写明：事故剧本 → 根因 → 为何应用层修不了 → 引入后验什么、怎么验。
> **R3 升级不得破坏已实证的正确性资产。** 本样例已实证资产（心跳兜事件、seq 幂等、台账单写铁律、流水 CAS、心跳对账豁免系）若被升级消解/作废，必须显式宣告并给出替代（见 §7 资产迁移表）。

## 1. 评估基线：物理单机部署 × 逻辑形态不可信（2026-09-08 定稿）

```
物理：一台服务器/一台开发机（平台 reason-main 8200 + 模拟器 reason-barrier-sim 8300 同机运行——开发与演示形态）
逻辑：平台(8200) ◄—— 不可信链路（延迟/丢包/乱序/单向断 可被注入器制造）——► 设备(8300，十公里外的杆)
```

| 维度 | 含义 | 对评估的影响 |
|---|---|---|
| **物理单机（部署事实）** | 双进程同机，回环链路质量极高 | 仅提供开发便利；**不构成任何机制豁免理由**（R1） |
| **设备不可信（逻辑标尺）** | 通道可能被截获/重放/注入/伪造；网络故障（延迟/丢包/乱序/单向断/平台重启窗口）真实存在 | 鉴权/防重放/重试/超时/对账全按不可信设计；故障场景由**应用层注入器**（sim 网络剧本）制造并在自动化验收中复现 |
| **注入器承重（v3.0 审计）** | 0.1-0.8 的故障验收剧本（单向断/卡滞不报 FAULT/MOVING 注入/事件丢失/乱序）全部由注入器实现，**现有 /sim/* 端点（fault/recover/tamper/vehicle）不足以支撑**——注入最小集（上行/入站方向断开关、卡滞不终态、MOVING 注入、事件丢弃/延迟）**随 0.1 同批先建**（0.1 验收前置，非阶段3 负载能力） |
| **非对称断连（逻辑推论）** | 单向断（只断 sim→平台 或 平台→sim）可被注入器制造 | 平台对设备唯一信息源=上行，上行断即失明（即使下行通、即使设备已执行）→ **T20 状态查询指令** |
| **平台会重启/故障** | 平台重启窗口内设备上报会失败（同机同样发生） | 上报可靠传输或显式重试；账本不许静默丢账（取舍见 §6 阶段2） |
| **规模会增长（几十→几百杆）** | 全表扫/逐台 HTTP/串行心跳会塌 | 任务/心跳/Redis 判定需批量与并行化；量由模拟器制造（阶段3） |
| **契约双方独立演进** | main 与 sim 同仓但可独立部署、独立发布 | 无共享 schema/无契约测试 = 必然悄悄腐化 |
| **管理端只信已授权用户** | RBAC 在位 | 授权入口防护（认证前置）与授权内一致性同等重要（T19） |
| **平台时钟可信、设备时钟不可信** | 单一时钟源 | 防重放设计以 nonce 单调为主，时间窗仅容差（豁免须显式，见 0.5） |

**部署形态注记**：跨公网/NAT/穿透类决策（frp、WebSocket 长连接、第二台云）**全部关闭**（用户 2026-09-08 定稿）；传输层加固（TLS/防火墙来源收敛）标注为"随部署形态启用"——物理同机时无实际暴露面可暂缓，但**应用层机制（0.1-0.8 全部修复）不因同机豁免任何一项**。

## 2. 红队问题总谱（三报告合并去重 + 审查增补 + 逻辑形态新增，共 20 项）

### T1 [P0] 信任链：共享静态口令 + 无个体凭证 + 无签名 + 无防重放——单点泄露全盘可控
- **证据**：口令 `barrier-sim-token-2026` 明文双侧 yml（main application.yml L92 / sim application.yml L15）随仓库分发；唯一校验 = [DeviceChannelProperties.matches](reason-main/src/main/java/com/reason/modules/device/config/DeviceChannelProperties.java) 固定串常量时间比对，无过期/无 per-device 密钥；事件/心跳表单只有 {deviceNo, state}，无签名/事件号/时间戳；HTTP 明文。
- **剧本**：持有口令冒充任意已登记设备——①伪造 FAULT → 台账 FAULT → AutoTask 仲裁4 永久停自动（DoS）；②伪造 UP/DOWN 到位事件 → 在途流水被销账（审计说谎）；③截获心跳无限重放 → 对断链设备"假活"；④伪造心跳+吞真实事件 → 诱导平台反复驱动真实设备（物理风险）。
- **修复方向（0.5）**：per-device 独立 secret + HMAC-SHA256 签名（**事件与心跳双通道同权**，防重放 nonce 沿事件序号体系单调递增为主、时间窗仅做容差并显式豁免"设备时钟不可采信"边界——不依赖设备可信时钟）；**secret 注入路径规定：环境变量/外部配置，仓库零明文**；登记/生成路径与"轮换后旧 secret 即刻失效"验收；HTTPS 随部署形态启用（传输层加固 P2，物理同机暂缓——T1 应用层凭证部分不随形态）。**实现定序：验签在 XssFilter 之前完成（XssFilter 重写 body，先验签后清洗），或 device 通道从 XSS 重写豁免**。

### T2 [P0] 上行事件语义：事件无 commandSeq/无 eventSeq——平台"按动作猜流水"，伪造/重放/乱序/丢包使审计永久说谎
- **证据**：[DeviceEventServiceImpl](reason-main/src/main/java/com/reason/modules/device/service/impl/DeviceEventServiceImpl.java) L40-49：UP→`markArrived(deviceNo,"OPEN")`、DOWN→`markArrived(deviceNo,"CLOSE")` 按"设备+动作名"反推指令；markArrived 取最近一条同动作 PENDING（[DeviceCommandLogServiceImpl](reason-main/src/main/java/com/reason/modules/device/service/impl/DeviceCommandLogServiceImpl.java)，秒级 createtime 排序，同秒多条时目标不确定）销账，终态无证据驱动反证路径；sim 上报 body 同构无引用；上报失败仅 log.warn 不重试。
- **剧本**：①重放合法 UP → 未执行指令被标 ARRIVED；②重放旧 FAULT → 在途 PENDING 全断 EXEC_FAILED，随后真实 UP 无 PENDING 可销（杆健康、审计"执行失败"）；③乱序迟到事件盲目覆盖台账（事件通道无心跳同款 grace/单调守卫）可回退 MOVING（联动 T6）；④回执丢失假账：SEND_FAILED 永不因后续到位事件反证为 ARRIVED；⑤事件丢失→心跳校正必过 grace → **每次正常动作的事件丢失都触发"状态漂移"误告警**（正常与异常不可区分）。
- **修复方向（0.1，协议 v2 一次定稿）**：事件携带 `commandSeq`（设备回显触发指令）+ `(bootId, eventSeq)` 双元组（bootId=设备重启代际，解决重启后 seq 归零被旧序守卫误拒——MQ 时代无连接语义，重启自述与积压旧事件靠 bootId 区分）；平台按 (deviceNo, commandSeq) 精确闭环；台账冗余 last(bootId,eventSeq) 条件更新（旧序拒绝；bootId 变化且身份已验证则接受并重置基线）；流水增证据驱动反证路径（SEND_FAILED→ARRIVED 需到位事件+seq 证明）；心跳对账"自述与在途指令目标一致则豁免告警"。**协议分两层定稿：语义层（事件结构/bootId/seq/HMAC 载荷，与载体无关）+ 传输适配层（HTTP header vs MQ property），避免搬家二次定稿。** **逻辑形态增补（必做，P6/P7）：sim 事件上报失败必须退避重试（现仅 log.warn 丢弃——回环不丢包导致该路径测不出，须靠注入器制造事件丢失才能验证；重试靠 eventSeq 幂等去重）；心跳对账 grace 窗口参数化并按注入器剧本标定（回环无抖动下固定 3s 永不触发容差路径，注入延迟/丢包后要么误判漂移要么漏真漂移）**。

### T3 [P0] 下行 /cmd 与 /sim/* 控制面完全无鉴权——攻击者可绕过平台直控"杆"（级别按形态假设判定，与 127.0.0.1 当前绑定无关）
- **证据**：sim [CommandController](reason-barrier-sim/src/main/java/com/reason/barrier/controller/CommandController.java) `/cmd` 无任何校验；[SimController](reason-barrier-sim/src/main/java/com/reason/barrier/controller/SimController.java) 注入端点同无鉴权；平台 dispatch 不带任何凭证。绑定 127.0.0.1 只在同机联调成立（形态假设下 8300 必然对外可达）。
- **剧本**：任何能连 8300 的实体直发 OPEN/CLOSE——**绕过平台全部审计（@SysLog/流水/保持期），链深于 T1（连账本都没有）**；攻破 sim 后用 /sim/tamper 伪造状态上报污染台账 → 驱动平台对真实设备下发指令。
- **修复方向（0.5）**：下行复用与上行同源凭证（平台下发带签名头，sim 校验）；/sim/* 管理面与 /cmd 设备面分离（端口或网络策略）+ 独立鉴权；指令防重放并入 seq 体系。

### T4 [P1] 手动保持期只挡 AutoTask，挡不住 MonitorTask 超时重试——"人控 vs 自动"打架经重试通道复活
- **证据**：[BarrierAutoTask](reason-main/src/main/java/com/reason/modules/device/task/BarrierAutoTask.java) L95-99 仲裁1 查保持期；[BarrierMonitorTask](reason-main/src/main/java/com/reason/modules/device/task/BarrierMonitorTask.java) L78-96 retryPending 无保持期检查。
- **剧本**：应然 DOWN 时 AutoTask 发 CLOSE seq=10（60s 未到位）；管理员手动升杆（保持期 30min）；MonitorTask 无视保持期重发 CLOSE → 反向落杆打断人工控制（物理事故面）。
- **修复方向（0.2）**：MonitorTask 重试路径复用 AutoTask 仲裁（保持期检查 + 流水代际检查：存在更新的手动流水则跳过重试只告警）；重试对象限定"全局最新一代指令"；旧代际流水 SUPERSEDED。**并修保持期语义漏洞：保持期只在 dispatch 受理（code=0）后写入**——现状 [ManualHoldAspect](reason-main/src/main/java/com/reason/modules/device/aspect/ManualHoldAspect.java) proceed 前写 key：设备离线/被拒/失败的点击也会留下 30min 让位窗；持 close 权限低权账号每 20min 对已 DOWN 设备发一次被拒 CLOSE 即可全天候压制自动规则。

### T5 [P1] AutoTask 对"不报 FAULT 的受阻设备"无熔断——与告警"转人工"矛盾，无限物理轰杆
- **证据**：AutoTask 停自动唯一条件 actual==FAULT；sendByRule 失败仅 markSendFailed+log.warn，无告警无熔断。
- **剧本**：机械卡滞但状态机未到 FAULT → AutoTask 每分钟新 seq OPEN → MonitorTask 同 seq 重试 3 次 → RETRY_EXCEEDED 告警"转人工" → 下分钟 AutoTask 又发新一代 seq……"已判死"设备被无限轮番驱动。
- **修复方向（0.3）**：AutoTask 每设备"最近 N 次校正均未闭环 → 停自动 + AUTO_CORRECT_FAILED 升级告警"熔断（Redis 计数或查未终态流水）；停自动判据从"设备自认 FAULT"扩为"平台观测连续失败"。

### T6 [P1] MOVING 卡死静默停摆——台账卡 MOVING 零告警零处理
- **证据**（三层全漏）：AutoTask L105 仲裁3 MOVING return；[DeviceMonitorServiceImpl](reason-main/src/main/java/com/reason/modules/device/service/impl/DeviceMonitorServiceImpl.java) L63 stable 只认 UP/DOWN/FAULT（心跳自述 MOVING 永不比对）；monitorTask 只扫 PENDING+离线，无任何任务扫"卡 MOVING"。
- **剧本**：伪造 MOVING 事件或设备真卡 MOVING 不报 FAULT → 台账 MOVING → 自动升降全部让位 → **无任何告警**（静默故障，最危险形态）。
- **修复方向（0.4）**：monitorTask 增"台账卡 MOVING 超阈值"扫描（阈值>动作耗时上限）→ 告警交人工（铁律：只喊不改状态）；管理端告警确认路径同批落地（见 T10）。

### T7 [P1] FAULT 到达通道不同 → 同一物理故障产生不同账本终态与告警类型
- **证据**：FAULT 走事件通道 → markExecFailed 中断在途 PENDING + DEVICE_FAULT 告警；FAULT 走心跳通道 → 只 raise(DEVICE_FAULT) 不中断在途，若台账≠FAULT 还先落 STATE_MISMATCH。
- **剧本**：卡杆 FAULT 事件丢失、心跳携带 FAULT → 在途不中断 → monitor 对故障设备重试 3 次 → RETRY_EXCEEDED；事件没丢则 EXEC_FAILED。**账本终态由"哪条通道先到"决定**。
- **修复方向（0.6）**：心跳 FAULT 路径补 markExecFailed（FAULT 是设备物理态，与通道无关，收尾必须一致）——**前提是心跳纳入 0.5 签名与防重放，否则等于给攻击者一条新的"打断在途流水"通道**（修复后重攻击检验：T7 修复必须与 T1 双通道同权加固绑在一起实施，顺序 0.5→0.6 不可倒）。

### T8 [P1] 被拒指令不占 seq 线 → 后续高 seq 受理后其重试被"幂等忽略"永久吞掉
- **证据**：sim [Barrier](reason-barrier-sim/src/main/java/com/reason/barrier/model/Barrier.java) lastSeq 只在受理时推进；`seq<=lastSeq` 一律按重复返回 code=0；平台 retryPending 对 code=0 视为成功只增计数。
- **剧本**：指令 A(seq=a) 在 MOVING 时被拒且留 PENDING → 指令 B(seq=b>a) 受理后 lastSeq=b → 重试 A 被幂等忽略 code=0 → A 永不执行也永不拒绝，重试烧完落 RETRY_EXCEEDED 误导人工。
- **修复方向（0.6）**：sim 区分"已执行 seq"与"已拒绝 seq"两条线（重试曾拒绝过的 seq 回专门原因码）；平台对被拒指令直接 markSendFailed 不进重试队列（现状对被拒不落地状态是缺口）。

### T9 [P1] 错误语义两处不对称——token 漂移/协议垃圾/设备离线互相不可区分，静默腐化
- **证据**：sim 拒绝是业务码（HTTP 200 {code:1}），协议垃圾（非字符串强转）走 500；平台 dispatch 只认 code==0，HTTP 500/连接异常统一抛"设备无响应"——协议违规与真离线不可区分；反方向：平台业务拒绝返回 HTTP 200+{code:500}（RRExceptionHandler 不设 HTTP 状态码），而 sim 两侧 reporter 只看 HTTP 状态不读响应体 → **token 漂移时 sim 记"[上报成功]"，设备侧自省窗口失明**。
- **修复方向（0.7）**：平台业务拒绝改 HTTP 4xx/401；sim 校验响应体 code 非 0 时 warn；sim 强转输入回 code=1 不 500；平台按 4xx/5xx 细分 SEND_FAILED 原因（离线/拒绝/协议错）；双侧 token 启动互检。

### T10 [P1] 告警无处理闭环——alarm_handled 恒 0，无确认/恢复/清除语义
- **证据**：全局无任何 `setAlarmHandled` 写 1 的调用点；[DeviceAlarmController](reason-main/src/main/java/com/reason/modules/device/controller/DeviceAlarmController.java) 只有 list；schema 注释与代码无对应。
- **后果**：设备离线→告警；恢复在线→无自动关闭无恢复记录；告警表单调膨胀，未处理列表永远等于全表——运维无法区分"此刻真故障"与"历史故障"，应急通道疲劳失效。
- **修复方向（0.4 最小集 + 阶段4 增强）**：0.4 提供确认接口（handled=1+处理人/时间，@SysLog 留痕）+ 列表默认只出未确认 + 设备恢复事件（到位/心跳稳定）反向标记同设备未处理告警——**与 0.4 MOVING 巡检联动：巡检告警后必须能"处置+关闭"，否则告警只喊无闭环**；阶段4 再做风暴限速与看护增强。

### T11 [P1] 心跳节拍串行塌缩 + 无连接池——逻辑形态下首日即触发（故障注入即复现）
- **证据**：[HeartbeatReporter](reason-barrier-sim/src/main/java/com/reason/barrier/reporter/HeartbeatReporter.java) 单线程逐设备同步阻塞；scheduleAtFixedRate 无重叠；RestTemplate 用 SimpleClientHttpRequestFactory（**每次请求新建 TCP 连接，无连接池/无 TLS 会话复用**）；connect/read 超时 2s（同机标定）。
- **逻辑形态重判**：设备链路不可信（R1）下，网络故障注入（延迟/挂起）会使单台上报阻塞从"罕见"变"高频"——2 台设备即可使一轮心跳 >10s 间隔（scheduleAtFixedRate 直接跳轮），TTL 30s 判活失真、误 OFFLINE 刷屏；注入器按"延迟 0.5-2s + 丢包"剧本即可在本地复现。无连接池使每次心跳/事件都付一次 TCP 握手。
- **修复方向（阶段 0 工程收尾）**：心跳并行化（共享线程池限并发/每设备独立超时）；失败设备跳过不串行阻塞；上报/下发引入 HTTP 连接池；超时参数化入 yml（可配 5-10s）并按注入器剧本标定。

### T12 [P1] 任务失败静默记账——根因系统性丢失，应用日志零痕迹
- **证据**：[ScheduleJob](reason-main/src/main/java/com/reason/modules/job/utils/ScheduleJob.java) L54-78：反射异常必然包 InvocationTargetException，`log_error=substring(e.toString())` 不含根因；失败日志行全注释；不重抛 JobExecutionException。
- **后果**：barrierAutoTask/barrierMonitorTask 内部任何失败，schedule_job_log 只落一行 InvocationTargetException 无法定位；error.log 无记录；双实例后放大。
- **修复方向（阶段1a）**：catch 内取 e.getCause() 打印堆栈；log.error 带 jobId+根因；可重抛 JobExecutionException 使 misfire 链路可见（与 DoNothing 语义评估）。

### T13 [P1] 调度并发与集群启动竞态——任务可重叠 + 双实例第二节点启动失败
- **证据**：ScheduleJob 无 @DisallowConcurrentExecution；[ScheduleJobServiceImpl](reason-main/src/main/java/com/reason/modules/job/service/impl/ScheduleJobServiceImpl.java) @PostConstruct init() check-then-create 非原子 → 双节点同启第二节点 ObjectAlreadyExistsException → **Bean 初始化失败整个应用起不来**。
- **剧本**：单轮执行超周期 → 同任务两实例并发：AutoTask 双实例各取不同 seq → 同动作两条指令两次物理动作；MonitorTask 双实例同 seq 重发 + retry_count 双份自增越上限。
- **修复方向（阶段1b）**：ScheduleJob 加 @DisallowConcurrentExecution（或任务内 Redis SETNX 执行权）；init 改"冲突即 update"幂等 + 挪 ApplicationReadyEvent 降级。

### T14 [P1] Redis 易失态无补偿——online/manual-hold/alarm-dedup 全丢后机制行为不一致（含人身安全剧本）
- **证据**：恢复机制只覆盖 cmd-seq（启动播种）；dev yml Redis 无密码 db15。
- **剧本**：Redis 重启/FLUSHDB → ①全设备 online 丢 → OFFLINE 告警洪峰（dedup 也丢，去重失效）；②AutoTask 仲裁2 全判离线停自动；③**manual-hold 丢 → 正被人手动接管/检修的设备即刻恢复自动对账——人在杆下时系统按时间规则自动升降（物理风险，全文最重剧本）**；④告警刷屏。
- **修复方向（0.8 保持期优先 + 阶段1 其余）**：保持期落 DB（与 Redis key 双写，Redis 丢失后从 DB 重建）——0.2 修保持期语义但 key 仍是易失的，0.8 补持久化才算修完一半；online key 启动宽限（平台重启后 N 秒内不判离线，防重启自伤误报）；告警去重 DB 时间窗兜底；生产 Redis 密码+持久化。

### T15 [P2] 管理端分页无校验无上限 + N+1 Redis——低权用户可做 DoS，非法输入一律 500
- **证据**：三处 service Integer.parseInt 直接解析无范围校验 + 每行一次 hasKey；表单无 @Min/@Max。
- **修复方向（阶段1a）**：表单校验（page≥1、limit≤200）或 clamp；在线状态 Redis pipeline/multiGet 一次往返。

### T16 [P2] 配置安全——默认 dev profile + 全明文凭据 + 白名单幽灵路径 + jasypt 半成品
- **证据**：application.yml L20 默认 `active: dev`；prod yml 也是 root/root 明文（注释与事实矛盾）；白名单含已无 Controller 的 `/test/**`、`/aaa.txt`、`/app/**`、`/etc/test/**` 幽灵路径与 `/druid/**`（druid 开关一旦打开即裸奔）；jasypt 配置齐全但全仓无 ENC() 生效值；CORS `allowCredentials(true)+allowedOriginPatterns("*")`（管理端一旦有存储型 XSS，token 可被任意源持读全接口）。
- **修复方向（横切治理）**：删默认 profile（缺 profile fail-fast）；prod 凭据环境变量/ENC() 化；白名单收敛最小集并逐条对 Controller 存活核对；jasypt 闭环或删除；CORS 收敛到实际前端源。

### T17 [P2] 可观测性断裂——跨进程 trace 无、报文无留痕、指标无、sim 日志即焚
- **证据**：平台 TraceIdFilter 只吃入站 X-Trace-Id；sim 无任何 MDC/无 logback 文件配置；dispatch 不带 trace header；/device/event|heartbeat 不落请求日志；无业务指标；logback 三处 maxHistory 全注释 + warn/error 分桶互斥（WARN 文件看不到 ERROR）。
- **后果（事故推演）**："事件通道中断 5 分钟"能定位到"通道级+时间窗"（台账/流水/告警三表互证），**到不了报文级**（哪几次上报到达、丢在哪一跳）。
- **修复方向（阶段4）**：sim 最小可观测（文件 appender+trace 生成与透传）；dispatch/事件/心跳链路 X-Trace-Id 贯穿；事件/心跳入口结构化日志；logback 修复（maxHistory + ERROR 桶 ThresholdFilter 吸收 WARN）；任务看护（最后执行时间超阈值落 ERROR+告警）。

### T18 [P2] 质量门缺口——CI 不覆盖 sim、契约无测试、平台 device 域近乎零单测
- **证据**：根 pom 仅聚合 reason-main，ci.yml 只在根 mvn verify → sim 的 BarrierTest 10 用例永不在 CI 跑；ci.yml 含遗留分支 refactor/parking-rebuild；平台 device 域唯一测试 = BarrierTimeRuleTest；sim 测试缺口 E1-E14（附录 A）；契约一致性只靠两端注释互相声明。
- **修复方向（阶段 0.0 前置，先于一切协议改动）**：CI 加独立 job 跑 `mvn -f reason-barrier-sim/pom.xml test`（sim 单测纯 JUnit 无 Docker 依赖，直接可绿）；契约冒烟两步走——先轻量共享契约样例（`contracts/` 共享 JSON 报文+字段+seq 语义，两侧单测读取断言）+ sim E11 controller 契约表测试（不引 Pact），再双进程端到端（main jar+sim jar+Testcontainers MySQL/Redis，运行手册剧本转断言脚本，起步 allow-failure）；**顺序约束：sim CI 必须先于阶段0（0.1/0.5/0.7 是双端锁步改协议，无 CI 钉住即回退 T18 老路）**。

### T19 [P1]（审查增补）认证前置缺口——验证码关闭 + 无限尝试 + XFF 可伪造 + 锁号 DoS
- **证据**：[SysLoginController](reason-main/src/main/java/com/reason/modules/sys/controller/SysLoginController.java) L82-85 验证码校验整体被注释；[SysUserServiceImpl](reason-main/src/main/java/com/reason/modules/sys/service/impl/SysUserServiceImpl.java) 锁定仅 attemptLimit!=0 生效而种子值='0'（不做限制）→ 无限次在线尝试零节流；[IPUtils](reason-main/src/main/java/com/reason/common/utils/IPUtils.java) 直接信任 x-forwarded-for → 伪造绕过；尝试计数按 loginname 无 IP 维度 → 爆破可顺手锁死运维账号（可用性 DoS）。
- **影响链**：管理端持有 device:command:open/close 与 @ManualHold，账号沦陷 = 远程真实驱动杆（与 T1-T3 同级物理风险面）。**平台若对外可达（云部署形态），此缺口从"框架债务"升为"上线阻断项"**（见 §6 逻辑机制清单）。
- **修复方向（框架级）**：验证码恢复或按 loginname+IP 双维度限速；attempt_limit 默认值改非 0；XFF 只在可信代理后取末跳；锁号 key 加 IP 维度防锁号 DoS。

### T20 [P1]（逻辑形态新洞）协议缺"状态查询"指令——非对称断连/上行故障时平台失明，销账/重试/熔断基于陈旧台账误判
- **证据**：协议只有下行 OPEN/CLOSE + 上行 event/heartbeat（**无平台→sim 的查询指令**）；[BarrierMonitorTask](reason-main/src/main/java/com/reason/modules/device/task/BarrierMonitorTask.java) L66-76"先对账销账"查的是**自己写的台账快照**（recordDao.selectOne），而上行断时台账已陈旧——销账/重试/熔断（T5）全部基于陈旧快照决策；sim 的 /sim/status 是本地操控台（无鉴权且非平台协议）。
- **逻辑形态剧本（注入器制造）**：注入"sim→平台方向断"（平台→sim 通）→ 平台下发 OPEN → sim 执行成功 → 事件+心跳均上不去 → 平台超时重试同 seq（sim 幂等忽略 code=0）→ RETRY_EXCEEDED 误告警 → T5 熔断停自动 → **设备正常、下行正常，平台却判定故障并停摆**。反向（平台→sim 断）的真实语义（与 T9 一致）：sim 未执行但平台每次 dispatch 显式 SEND_FAILED"设备无响应"——平台**知道下发失败**（不存在"以为已下发"）；危害是心跳仍通（上行在）时"台账在线与指令全失败并存"，平台无法区分链路断/协议错/设备拒（T9 未修前），重试在断链期耗尽→误 RETRY_EXCEEDED；QUERY_STATE 同向不可达，恢复后靠心跳自述对账才能暴露"未执行"。
- **修复方向（0.1 协议 v2 范围）**：新增 `QUERY_STATE` 指令（平台→sim 主动查询，sim 即时应答：当前状态 + bootId + lastEventSeq + 最近指令 seq/结果）——MonitorTask 超时对账改为**先发查询再决策**（查询设备实况，替代查自己快照）；查询指令同时是人工诊断通道与上行故障时的唯一窗口；查询结果入日志留痕（查询非动作，不进 command_log）。

## 4. 应急处理性评估（事故推演结论，逻辑形态版）

剧本①"事件通道中断 5 分钟"（注入器制造，同机可复现）——结论不变：**能回答"发生了什么/何时/哪台/业务是否自愈"（三表互证），到不了报文级**；且事件与心跳同向同链路，事件丢时心跳大概率也受影响——软补账路径并不可靠兜底。

剧本②"非对称断连：sim→平台断、平台→sim 通"（注入器制造）：**平台失明**——指令已执行但无任何反馈通道，MonitorTask 对账查自己写的陈旧台账 → 误告警/误熔断（T20）；现资产完全无法定位（无查询指令、无下行回执）。此剧本是 T20（QUERY_STATE）的硬依据。

- **结论**：业务自愈设计从"达成目标"降级为"尽力而为"——软补账窗口（10~60s）在故障剧本下常态出现且可能双向同时失效；运维排障资产（trace/报文/日志/查询通道）与逻辑机制清单（§6）同步补齐。

### 阶段 2：RocketMQ 可靠事件通道（决策门！go/no-go 由用户拍板）

**先做目标取舍（这是产品决策，不是红队剧本能单方面逼出的）**：
- 现状自愈 SLA：事件丢失 → 心跳软补，台账 10~60s 收敛，流水靠 MonitorTask"补证销账"——已实证达成（§4）。
- MQ 的独有增量（0.1 修复后仍残留的洞，显式列出）：①**审计时间精度**：流水"真实到位时刻"在事件丢失场景只能间接补证，无法回答"几点几分几秒到位的"；②**平台重启窗口内的每起动作**都产生一次补证往返与残余漂移窗口（0.1 豁免告警后仍有一次静默补账）；③事件丢失窗口内"台账短暂失真"（几秒~60s）在展示/下游对账中可见。**若这些增量不在目标内 → go/no-go 判 NO，MQ 写主线 backlog（预研属性不变）**。
- 量级预算：当前 N=50×10s≈5rps 心跳+稀疏事件，HTTP 直连无压力——**MQ 理由不得建立在当前量级上**；量的问题由阶段3 模拟器制造洪峰实证（心跳洪水剧本），那是验证路径不是砍架构理由，但也不构成"现在就要"的理由。结论：**阶段2 的正当性 = 审计完整性目标取舍，不是容量**。

**理由链（每条标注对 D3 的依赖）**：
1. 账本完整性（目标取舍后成立）：事件一次投递 broker 成功即不丢，平台重启完续消费，流水终态不需要"补证销账"间接路径（依赖 D3=事件走 MQ）。
2. 洪峰削峰：仅当心跳同走 MQ（D3=同走分支）才由 broker 吸收；心跳留 HTTP 则此条失效（依赖 D3）。
3. 集群消费语义：双实例平台事件负载均衡、消费幂等（0.1 后事件天然可重放）（依赖 D3）。
4. sim 简化：去掉 HTTP 自省窗口——**边界：producer 端重试语义仍须保留**（broker 故障时 sim 要能缓冲/重试，与阶段3 混沌剧本衔接）（依赖 D3）。

**边界（必须写清）**：MQ 只解决可靠传输，不解决 T1 身份伪造/T2 语义绑定/T6 MOVING——那些在阶段0 应用层；引入后 HTTP 事件通道退役（**回滚路径=双写期过渡，见 D6**）；broker 独立于平台部署（本机安装仅开发联调，不因同机豁免 broker ACL/TLS 接入安全）。

**接入与测试策略（环境分裂是最大落地风险）**：本地 Windows 原生 RocketMQ 5.3.1 vs CI ubuntu runner 无 broker。分层方案：①协议/消费幂等纯逻辑入平台单测（注入消费回调，不连 broker）；②端到端"生产→消费→积压→重启续消费"IT 标 @Tag("mq") 独立 job，CI 用 rocketmq 容器（Testcontainers GenericContainer 链式 namesrv+broker，冷启动 30-60s）跑；③若评估 CI broker 不稳，**显式声明**"MQ 端到端仅本地手动验证+剧本文档化，CI 只编译+单测"——必须写出来，不许沉默带过（T18 老路重演）。客户端选型（4.x remoting rocketmq-spring-boot-starter vs 5.x gRPC rocketmq-client-java）在接入时定并记版本。

**验收**：平台重启 60s 期间设备上报 N 起事件 → 重启后全部消费、流水终态一致（真实到位时刻可答）；重复投递被幂等吞掉；积压期间心跳判活无误判（视 D3）；sim 在 broker 故障时上报不丢（缓冲+重试）。

## 8. 待拍板决策点

- **D1 块序**：阶段 0.0 → 0 → 1 →（2 go/no-go）→ 3 → 4。我的主张不变：0.1 协议先行（T2 是 T6/T8/T10 的根；协议 v2 必须早于阶段2，否则 MQ 里跑带洞协议）。
- **D2 设备凭证形态**：per-device 静态 secret（HMAC+nonce，够样例，0.5 范围）vs 注册制动态令牌（近真实 IoT，主线立项）。倾向前者；注册制留主线（与多租户 B 同批）。
- **D3（决策门，阶段2 前置）心跳是否与事件同走 MQ**：**明确主张：事件走 MQ、心跳留 HTTP**——①两种信号服务质量诉求相反：心跳要"有界时延"（TTL 30s 判活），MQ 提供持久可靠但时延方差为代价，同走 = 判活退化为"消费延迟函数"（平台重启积压窗口下误判 OFFLINE 风暴 + AutoTask 仲裁2 冻结），复杂度从网络层转移到消费层；②心跳留 HTTP 提供**故障域隔离**：broker 故障时 liveness+自述对账仍活，双通道互补资产存续（角色从"事件丢失兜底"降级为"broker 故障兜底"，非删除）；③真实 IoT 形态即"业务数据走可靠消息、保活走连接层"。**注记（单机回退后）：同机回环下两通道底层质量趋同，D3 差异纯来自 broker 故障域与 QoS 语义（论据②③为主），与网络形态无关，立场不变。**若最终选同走，必须补三前置：TTL 判活按消费时间重锚+启动宽限期；每设备 keyed 有序投递（禁默认轮询跨队列乱序）；阶段3 实测消费延迟 P99 vs TTL 余量 ≥3× 裕度。
- **D4 双实例时机**：阶段1 完整做（T12/T13 是前置，不可跳过）；不依赖阶段0。
- **D5 MQ 消费幂等与每设备有序性**：0.1 的 seq 守卫抗重复投递但**抗不了跨队列乱序**（迟到的真事件会被当旧序拒=丢数据）。决策：单队列 vs 设备 keyed 分区 vs 每设备队列，及对双实例消费并行的约束——0.1 与阶段2 的接缝，须在协议 v2 定稿时定方向。
- **D6 HTTP 事件通道退役时机与回滚**：阶段2 建议"双写期"（事件同时发 HTTP 与 MQ，平台以 MQ 为准并校验一致，阶段3 回归通过后退役）——否则 MQ 侧事故只能整体回滚代码。
- **D7 事件时间基准**：积压消费下平台写台账/流水用"处理时刻"还是"事件携带语义时间"？涉及异地设备时钟（单一时钟源边界的显式豁免面，与 0.5 nonce 设计同源）——建议：处理时刻为准+事件内记录设备采样时刻仅供诊断（不参与业务仲裁），若需业务仲裁再议。
- **D8 告警全局限速归属**：T14 DB 时间窗兜底 + 批量 OFFLINE 限速——归 0.4/阶段4 T10 定义内，不留散件。
