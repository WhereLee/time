## 方案 1（P0）：HTTP 事件入口必填校验，消灭 500

- [x] 实施
- [x] 单测
- [x] 回归（全量 189/189 绿 2026-09-11）

**根因**：`DeviceEventController` 未校验 `bootId/eventSeq` 必填；`DeviceEventServiceImpl` 把 `Long eventSeq`
传入 `updateStateByEventWithSeq(..., long)` 拆箱 NPE → 500。MQ 侧已有必填校验，HTTP 侧缺失——
违反契约 §5"协议垃圾 → 400"。

**改动**（单点收口，双入口同获益）：
- `DeviceEventServiceImpl.handleStateEvent` 首行加必填断言：`deviceNo/state/bootId/eventSeq` 任一空
  → `throw new RRException("协议v2事件缺必填字段...")`；HTTP 侧现有 `catch (RRException) → 400`、
  MQ 侧现有 `catch (RRException) → ACK 毒消息` 均自动正确。
- 控制器不加重复校验，保持入口薄。

**测试**：`DeviceEventServiceImplTest` 加 3 例——null eventSeq / 空 bootId / 全字段合法不误伤；
断言 `RRException` 而非 NPE。

**风险**：无（比现状严格，行为对齐契约）。**工时**：0.5h。

## 方案 3（P1）：跨代重放守卫（bootId 历史集合）

- [x] 实施
- [x] 单测（事件 11 + 守卫 8）
- [x] 契约落档（PROTOCOL-V2 §3.3）
- [x] 回归（全量 189/189 绿）

**根因**：`updateStateByEventWithSeq` 对 `bootId≠lastBootId` 一律接受并重置基线；被截获的旧代际事件
可重放（状态回退；极端下误销在途流水）。协议把防重放托付给序守卫，但序守卫有代际盲区。

**改动**（协议线格式零变更，不动 DB 原子守卫）：
- 新 Redis key：`barrier:boot-history:{deviceNo}`（SET，成员=bootId，TTL 30 天）+
  `barrier:boot-current:{deviceNo}`（value=当前代际）。
- 收口在 `DeviceEventServiceImpl.handleStateEvent`（进入 `updateStateByEventWithSeq` 之前）：
  `bootId == current` → 直通（正常稳态零额外开销）；不等 → `SISMEMBER history`：命中=重放，
  `log.warn` 后 return（不更新台账不销账）；未命中=新代际，接受后 `SET current` + `SADD history`。
- Redis 异常 fail-open（放行 + WARN，降级为现状）。
- 附带收益：设备重启后 broker 迟到的旧代际事件重投会被正确拒绝（现状会被当"新代际"接受=真 bug）。

**测试**：`DeviceEventServiceImplTest`——新 bootId 首见通过并登记；已见 bootId 重放拒绝且不触 DB；
同 bootId 不查历史；Redis 异常放行。

**风险**：多实例下两个新代际并发竞争窗口（概率极低，退化为现状）；Redis 数据丢失后守卫失效
（文档明示）。**工时**：半天含测试。
