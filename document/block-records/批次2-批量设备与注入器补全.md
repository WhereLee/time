### EXPLAIN 索引验收（DoD）
```sql
EXPLAIN SELECT COUNT(*) FROM device_alarm WHERE device_no='BARRIER-B-01' AND alarm_type=2 AND alarm_createtime > unix_timestamp()-300;
-- key=idx_device_handled（possible_keys 含 idx_device_no_type_time），rows=1
-- 单设备等值下优化器选同前缀旧索引（代价相同），功能等价、毫秒级
EXPLAIN SELECT COUNT(*) FROM device_alarm IGNORE INDEX (idx_device_handled, idx_type_time) WHERE ...;
-- key=idx_device_no_type_time，type=range，key_len=139（三列全命中），Using index
```
结论：目标索引可用且覆盖查重条件组合（range+覆盖索引）；优化器在 device_no 等值+rows=1 时选 idx_device_handled 属正常代价决策（两者均 device_no 前缀定位）。配合 G2 实测 MonitorTask 0ms，量级目标达成。

## 五、边界/遗留（如实记录）
1. **乱序窗口被动超时**（规格 B8 已留档）：无独立定时器，仅来 1 条时靠"下一条事件到达"唤醒 5s 检查——布防后若设备再无任何事件，首条滞留至下一条事件（任意设备）触发；剧本正常用法（连续动作）不受影响
2. **Redis 5.0.14 稳定性**（本场环境级）：bgsave 伪 fork 崩溃嫌疑导致 11 小时窗口内 Redis→平台（Lettuce 超时风暴）→sim 连锁全灭。恢复后剧本全过；**本地 Redis 建议升级 ≥6.2**（可去掉 LUA 兼容层）或服务化托管——环境优化项，非代码缺陷
3. **sim 密钥文件**：gitignore 已补；密钥只存在本机文件+平台 DB（与既有密钥同安全域）
4. G3-1 实测路径与规格"SUPERSEDED"预期不同（MQ 先闭环 → ARRIVED）：属双写期设计内更优路径，无阻塞项；若未来 MQ 通道退役（批次3 判定），纯 HTTP 下乱序场景将走 monitor 代际裁决 → SUPERSEDED，届时回归验证
