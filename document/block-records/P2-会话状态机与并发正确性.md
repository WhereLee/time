## 核心设计：双层并发模型（守卫是快速失败层，条件更新是最终判官）

**入场**：①参数规范化（编号/车牌 trim+大写）②查车位（不存在/禁用拒绝）③**查重兜底**（idx_space_state：已有进行中会话拒绝）④**条件更新占位**（`UPDATE park_space SET state=1 WHERE space_id=? AND state=0`，行数 0=并发被抢先）⑤插入进行中会话。
③与④之间的并发窗口由④的行锁语义闭合——**正确性不依赖③**，③只提供快路径拒绝与友好错误。

**取消**：①查会话 ②守卫（终态不可取消，语义化快速失败）③**会话终态化条件更新**（`UPDATE park_session SET state=2... WHERE session_id=? AND state=0`，行数 0=并发下已被其他路径终态化，抛"状态已变更"）④**释放车位条件更新**（state=1→0；行数 0=会话与车位状态不一致的数据异常 → 回滚暴露，不静默卡死车位）。
③的加锁顺序保证：并发双取消时仅一方行数>0，另一方收到明确异常而非覆盖写入。

## 单测的两个 MP 适配坑（详见 pitfalls/）

1. **Lambda cache**：纯单测（无 Spring 上下文）下 LambdaQueryWrapper/LambdaUpdateWrapper 解析失败（`can not find lambda cache`）——需 @BeforeAll 用 `MapperBuilderAssistant + TableInfoHelper.initTableInfo` 手动初始化实体元数据
2. **insert 重载歧义**：MP 3.5.9+ BaseMapper 新增 `insert(Collection)`，`verify(dao).insert(any())` 编译歧义——失败路径的 never-verify 删除（异常断言已隐含校验先于写库），成功路径用 `captor.capture()` 不受影响

## 验证分层说明（讲解素材）

- 单测（mock）验证「分支逻辑与行数语义」：行数 0→拒绝、守卫矩阵、参数规范化——**但 mock 证明不了真实并发**
- IT（真库）验证「条件更新行锁语义」：双线程齐发仅一成功 + 库内最终状态（进行中会话 1 条、车位占用）——M0 验收 3「并发用例可复现」落点
- 若实现退化为"先查后写"（无条件更新），IT 会断言失败（两线程都成功）——IT 是并发方案正确性的守门人
