## 三、剧本与单测发现的三处真实修复（本批核心价值）

### 1. 熔断死锁解除（恢复标记完善·B-02 现场）
P1 基线发现 B-02 处于历史熔断态：窗口 3 条 AUTO_RULE 全失败、设备实际已到位（UP=应然）——**下发被熔断挡 → 窗口永远翻不了新 → 告警每 5 分钟重复喊话，永不解除**（设计时的"恢复后自动校正成功解除"路径在"静默恢复设备"上不可达）。
修复：`maintainFailStreak` 中设备已到位（实然=应然）时——放行（后续"应然=实然"自然 return，无下发风险）+ 关闭残留 `AUTO_CORRECT_FAILED`。现场验证：重启后 B-02 告警被关、噪声停止。

### 2. 离线设备排查前置（恢复标记完善·W-02 现场）
修复 1 部署后日志暴露第二处：**离线设备（W-02）进熔断判定每窗口 raise**——离线时既发不了指令也无从评估熔断，且离线设备永远无法靠下发产生新 ARRIVED 解除熔断（与 type2 离线告警重复喊话）。
修复：`reconcileOne` 顺序调整——离线检查（原仲裁2）前置到熔断维护之前。现场验证：W-02 熔断告警停止新增（存量见 §四）。

### 3. 异常摘要超列长（P4 首跑暴露）
P4 首跑 streak 计数与自动恢复全对、**但升级告警没出现**——schedule_job_log 定位：轮5 记录 `Data too long for column 'alarm_content'`（log_state=1，整轮对账被炸进失败记录）。根因：MyBatis 撞唯一索引异常 message=完整 SQL 文本（数千字符），直塞 varchar(512)。
修复双管齐下：① `brief()` 摘要截断至 200 字符；② 升级告警与主循环隔离（escalateIfFailing 包 try-catch）——**告警是附属副作用，绝不该反噬对账主流程**。重跑 P4 全 PASS。

### 附：单测暴露的阈值防御
纯单测中 `getAutoFailStreakThreshold()` mock 默认 0 → `recent.size()(0) < 0` 不放行 → 空窗口 allMatch=true 误走熔断分支 + `recent.get(0)` 越界。修复：`threshold <= 0` 时按放行处理（错位配置不炸路径）。
