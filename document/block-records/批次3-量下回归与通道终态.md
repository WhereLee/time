## 三、环境事故：Redis 旧 dump 导致 seq 回退 → 对账静默卡死（本批首要发现）

- **现象**：机器重启（用户手动拉起 Redis）后，16:03 起自动对账日志"发现偏差→下发校正指令"每轮 50 条打印，但**流水表零新增、台账不校正**。
- **取证链**：warn.log `Duplicate entry 'BARRIER-B-01-2' for key 'u_device_seq'`（对账处理单台异常跳过）→ `redis-cli get barrier:cmd-seq:BARRIER-B-01`=3/4（DB MAX=11）——**Redis 加载了旧 dump，seq 计数器回退**，INCR 出的 seq 撞 DB 唯一索引。
- **修复**：`_g4_fix_seq.ps1`——52 台（50 批量+2 日常）`barrier:cmd-seq:{deviceNo}` 对齐 `MAX(command_seq)`；16:06 起对账恢复，50 条自动校正全 ARRIVED、台账回 UP。
- **教训**：①Redis 是本机手动启动进程（非服务），机器重启必须手动拉起（已在运行手册固化）；②持久化策略裸奔的本地 Redis 会"数据回退"，与 DB 权威不一致时**失败面是静默的**（仅 WARN）。
- **遗留加固建议**（候选批次4/5）：a) 对账"单台异常跳过"连续 N 轮同设备命中 → 升级 ERROR/告警（当前设计只记 WARN 等自愈，持续性异常会无限静默）；b) `nextSeq` 加 DB MAX 兜底校验（防御 Redis 回退）。

## 四、测试稳定化与脚本踩坑

- **flaky 修复**（编入本批提交）：`BarrierTest.人工复位_回落并恢复` 在全量负载下偶发断言 `[MOVING, DOWN, FAULT]`——根因=测试自身竞态（waitForState 轮询到锁内 FAULT 后立即 recover，插进"置位→锁外上报"间隙）。修复=先 `waitForExactly(MOVING, FAULT)` 等上报到位再复位（贴近真实运维时序）；3 连跑全量 42/43 全绿。
- **脚本坑**（复用者注意）：①`Invoke-Mysql "-N -e ..."` 字符串拼接又踩"引号被当单参数"（mysql 打 usage 被 2>$null 吞 → 查询空 → `[int]""=0` 假通过）——固定用 splat：`& mysql "-uroot" ... "-e" $sql`；②Select-String 匹配 sim 日志中文不稳（文件 UTF-8 vs PS 默认编码）——日志取证 pattern 尽量用 ASCII（logger 名/字段名）；③已修正的 S1/S2 断言用日志字段（`device_state`/`command_status`/`alarm_type` 码值：OFFLINE=2）。
