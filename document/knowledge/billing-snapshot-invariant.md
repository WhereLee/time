# 知识点：订单快照——账务记录为什么必须不可变

> 关联：P1 决策（park_order 结算快照列组）
> 深度标记：能讲清"快照不是冗余，是事实记录"的语义差别

## 问题：订单存引用还是存快照？

反模式写法：订单表只存 `session_id`，展示金额时"现查会话 + 现查规则算一遍"。看起来省列、符合范式，实际会让**历史账目漂移**：

- **规则调价**：今天把单价从 2 元改成 3 元，昨天的订单下次打开金额变大了——用户看到的账单取决于"何时查"，而非"何时结算"
- **资源复用**：出场后车位被下一辆车占用、空间编号被改，历史订单的"停在哪"跟着漂
- **记录被改/被删**：会话补录、规则停用，订单失去解释依据

钱相关的记录是**审计与对账的事实**：对账时系统间对的是"当时那一刻的数据"，时间旅行式的现查让对账永远对不上。

## 快照的正确语义

订单生成时，把**结算依赖的全部输入**复制进订单行——这是"事件已发生，输入已固化"的事实记录（write-once），不是违反范式的冗余：

| 类别 | 快照列 | 为什么必须固化 |
|---|---|---|
| 业务属性 | plate_no / space_no | 出场后资源复用，现查会变 |
| 时间事实 | order_entry_time / order_exit_time / duration_minutes | 会话后续改动不影响已结算账目 |
| 计费参数 | unit_price_fen（单价）、amount_fen（结果） | 规则调价不影响历史订单 |
| 状态 | order_state | 单据自身生命周期（M2 扩展支付） |

判断一个字段要不要进快照的口诀：**"结算后这个来源还会变吗"——会变，就快照**。

## 与范式化的边界

- 快照冗余的是**跨表读取路径**，不是同一事实的两份拷贝——订单里的 exit_time 与会话的 exit_time 语义不同（订单的是"结算依据"，会话的是"设备上报时间"），来源相同但职责独立，必要时可在会话上留"已结算"标记防止同一字段被二次结算改写
- 真正需要避免的是"宽表无限冗余"——单据明细（M2 的优惠项、时段明细）应进子表，不是塞进订单行
- 若需要追溯"计费规则本身"（某单按哪版规则算的），单价快照不够时要规则版本化（fee_rule 加生效区间），属 M2 规则引擎范围

## 本项目落点（P1 已定稿）

park_order 快照列组：plate_no / space_no / order_entry_time / order_exit_time / duration_minutes / unit_price_fen / amount_fen + `u_order_session` 唯一索引兜底（会话与订单 1:1，防结算事务并发触发双单）。会话表**不放金额**——金额只诞生于结算动作，属订单事实。

## 一句话

账务表存快照不是冗余设计，而是**把"结算时点的世界状态"固化为不可变事实**；面试讲"为什么订单要冗余字段"要从审计与对账的不可变性切入，而非"查询方便"。
