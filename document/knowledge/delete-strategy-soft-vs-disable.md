# 知识点：删除策略——物理删 / 逻辑删 / 禁用态

> 关联：P1 决策（车位无物理删除、会话/订单只增不改）＋壳子 schedule_job 软删复活模式
> 深度标记："删除"在关系系统里从来不是简单 DELETE，三种策略的取舍是建模功力的体现

## 三种策略与各自的问题

**物理删除（DELETE）**：行消失。问题：
- 引用它的记录全部悬空（无外键时应用层浑然不觉，历史订单的 space_id 查无此位）
- 审计丢失（谁建过什么、什么时候建的，无从追查）
- 唯一约束复活陷阱：`space_no` 唯一索引下，物理删掉 A-001 后可以重建 A-001——看似方便，但历史会话里的 space_no 快照与新记录撞名，追溯含混

**逻辑删除（deleted 标志 / @TableLogic）**：行保留、标记删除。问题：
- 所有查询必须恒带 `deleted=0` 条件（@TableLogic 自动加，但要防止绕过 MP 的裸 SQL 漏条件）
- **唯一索引与复活冲突**：软删后 A-001 仍在表里，重建同名撞唯一索引 → 壳子 schedule_job 的解法是把删除标记写进唯一索引（`job_status` 0-有效 >0-无效，删除时 status=id 递增，`UNIQUE(job_bean, job_status)` 让"软删后同名可重建"成立）——巧妙但依赖代码纪律：删除必须是"status=id"而非 status=1，两次删同名会撞
- 壳子另一面教训：sys_role/sys_user 有 recycle/status 列但 `@TableLogic` **被注释掉**——列在、逻辑死，查询不带过滤条件等于没删，属于半吊子状态（要么做通，要么不做）

**禁用态（本项目）**：把"删除"建模为**业务状态本身**。车位删除 = `space_state=2`（禁用）：
- 语义最诚实：禁用是可逆的（解禁回来），物理删除不是
- 历史会话引用不悬空（车位记录永远在）
- 无唯一索引复活问题（不重建，禁用复用同一编号；若要求"禁用后编号可复用"，需编号-状态进唯一索引，M0 不需要——被禁用的车位编号保留不可复用，符合真实停车场语义：编号是物理位置的标识）
- 会话/订单天然"只增不改"（账务事实），连禁用概念都没有——它们没有删除需求

## 决策口诀

1. **有引用、有审计诉求、可能误操作** → 不做物理删除
2. 需要"列表默认隐藏但数据可查" → 逻辑删除（做通：@TableLogic + 唯一索引方案 + 全链路条件验证）
3. 删除本质是"不可用"且可逆 → **禁用态**（业务状态列，最干净）
4. 物理删除只留给：纯草稿/测试数据、有完整备份且确定无引用的场景

## 本项目落点

- park_space：禁用态（space_state=2），编辑接口的语义含"启用/停用"；无 delete 接口、无 delete 权限串（菜单 200-208 无删除按钮）
- park_session / park_order：无删除概念（终态不可逆 + 快照不可变），DB 无 deleted 列
- 教训引用：壳子 recycle 半吊子（列在 @TableLogic 注释）→ 新表不引入任何删除列

## 一句话

先问"删了这个东西，谁还在引用它、谁还需要追溯它"，再选策略；**禁用态把删除变成状态迁移**，天然绕开逻辑删除的条件污染与唯一索引复活难题。
