# 知识点：并发正确性三方案——条件更新 vs 先查后写 vs 唯一索引

> 关联：P1 决策（park_space 占用语义）＋P2 入场并发用例
> 深度标记：能画出并发窗口、说清每种方案的失效模式，是"并发正确性不是性能问题"的试金石

## 场景还原

两辆车几乎同时刷同一空闲车位的入场：请求 A 查状态=空闲、请求 B 查状态=空闲 → 各自放行创建会话 → **一个车位卖出两次**。这是 check-then-act 竞态——先读后写之间没有原子性。

## 三种方案与失效模式

**方案 1：先查后写**（select 状态 → 业务校验 → insert/update）
并发窗口无法闭合：两次 select 都可能在对方 write 之前完成。**任何"查了再写"都不能挡住并发**——这是数据库课程"丢失更新"的现实形态。只可作为兜底查询（一致性要求低或已由他层保证原子时）。

**方案 2：悲观锁**（SELECT ... FOR UPDATE）
把判定与写入串行化：第二个事务阻塞在行锁上直到第一个提交。正确但代价高——引入锁等待、死锁风险（多行加锁顺序不一致时）、长事务放大问题。适合"冲突概率高且业务必须排队"的场景（如抢唯一资源），停车场入场冲突是低概率事件，杀鸡用牛刀。

**方案 3：条件更新**（本项目，推荐）
把"占用"建模为空间表的可比较状态，用**一条 UPDATE 语句同时完成判定与写入**：

```sql
UPDATE park_space SET space_state = 1, space_updatetime = ? WHERE space_id = ? AND space_state = 0
```

- 行锁语义：UPDATE 先对命中行加排他锁再执行，判定与写入天然原子——第二个事务执行同语句时**阻塞在行锁上**，第一个提交后它重新评估 WHERE（innodb 当前读），`space_state` 已非 0 → 影响行数为 0 → 拒绝
- 应用层只需检查 `update 返回行数`：0 = 已被占/不存在，抛"车位占用中"业务异常
- 无锁等待业务逻辑、无死锁面（单行单语句）、无需应用层排队

**方案 4（伪）：唯一索引约束"进行中会话唯一"**
MySQL 8.0 无 partial index（部分索引），无法表达"仅 status=进行中 的行唯一"；用 generated column 模拟（`is_active = (state=0)` 参与唯一索引）是可行但隐蔽的花活——约束语义藏在表达式里，排查与演进成本高。且本场景的占用状态在**另一张表**（park_space），跨表约束数据库层面根本表达不了——这正说明"占用"必须建模成空间表状态列，条件更新才有落点。

## 本项目的落点（P2 实现）

入场事务 = ①条件更新空间表（行数 0 → 拒绝）②应用层查重兜底（`idx_space_state` 支撑：同车位无进行中会话）③插入会话。唯一索引只留给**天然唯一**的约束：`u_space_no`（编号）、`u_order_session`（一会话一订单）。

## 边界与前提

- 条件更新的前提是**状态可比较列存在**——建模时就要把业务状态设计成表的普通列，而不是"存在一条记录就算占用"
- 与隔离级别的关系：InnoDB 默认 RR 下 UPDATE 是当前读加排他锁，行为不依赖应用的事务隔离设置
- 条件更新失败后的提示要区分"不存在"与"已被占"（先查存在性再判断，或让调用方语义化）
- 高冲突场景（同一资源 90% 并发都会撞）悲观锁/队列反而更优——方案选择依赖冲突概率，不是越原子越好

## 一句话

并发正确的核心是**把"判定+写入"压缩进一个原子语句**；条件更新用行锁 + WHERE 状态语义实现无锁等待的原子切换，是 check-then-act 场景的最优解。
