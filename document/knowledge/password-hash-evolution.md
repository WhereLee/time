# 知识点：密码哈希演进与渐进迁移（MD5 → SHA-256+盐 → BCrypt）

> 关联：Security 迁移块（PasswordCodec 实现）＋「还用 md5 吗」讨论
> 深度标记：能讲清"为什么慢哈希"与"存量数据怎么迁移"两层，才算真懂

## 一、三代哈希的演进逻辑

**MD5（已废）**：快哈希 + 通常无盐。单轮运算纳秒级——GPU 每秒可算数十亿次，配合彩虹表（预计算常见口令哈希），弱口令秒破。MD5 已不属"加密"而是摘要，专门用于完整性校验尚可，口令存储禁用。

**SHA-256 + 随机盐**：盐（随机串逐用户）打破彩虹表复用，但仍**快**——抗预计算不抗暴力：8 位纯数字在 GPU 上仍是分钟级穷举。单轮快哈希的共同缺陷：**计算成本太低，离线爆破与在线攻击成本不成比例**。

**BCrypt（当前）**：Blowfish 派生，核心是**自适应慢哈希**——`cost factor`（工作因子，本项目 $2a$10$ 即 2^10 轮）把单次计算拉到约 50-100ms 量级，暴力破解成本随 cost 指数上升；**盐内嵌哈希串**（`$2a$10$` 后 22 字符是随机盐），无需单独存盐列；每次编码盐随机，同明文两次哈希不同。

## 二、渐进迁移：为什么不能"直接换算法"

哈希单向不可逆——存量 SHA-256 串**无法离线批量转成 BCrypt**，只能让用户在登录时自然完成：

1. `PasswordCodec.matches` 按前缀分流：`$2` 开头走 BCrypt 验证；否则按遗留 SHA-256 语义验证（本项目为 `SHA-256(salt‖pwd)`，与 Shiro SimpleHash **位级兼容**——字节序颠倒则存量用户全部登不进，此结论已固化为单测断言）
2. 验证通过且是遗留格式 → **登录成功即重哈希**写入 BCrypt（`SysUserServiceImpl` 登录升级段）——用户下次登录起走新格式，存量用户"用一次迁移一个"
3. 全部存量用户登录一遍后旧分支成为死代码（可观察 `isLegacy` 命中率为 0 后删除）

优点：零停机、无感知；代价：迁移周期依赖用户活跃度——长期不登录的账号始终是旧格式（可接受，仅遗留兼容分支常驻）。

## 三、关联考点

- **DelegatingPasswordEncoder**（未启用，可选迭代）：Spring Security 官方机制——`{bcrypt}$2a$...` / `{sha256}...` 前缀标记编码器族，编码时自动写前缀、验证时按前缀路由，把"手写前缀分流"替换为框架机制；可注册自定义 sha256 编码器容纳遗留格式
- **BCrypt 72 字节上限**：超长口令被截断（业界用先 SHA-256 再 BCrypt 的方案处理，但引入双哈希要谨慎）
- **慢哈希的代价面**：登录接口被恶意灌请求时，BCrypt 本身就是放大攻击面（每次验证 50ms+CPU）——需要登录限流/锁定兜底（壳子已有 Redis 尝试次数锁定，见 roadmap/login-attempt-guard）
- 面试追问常见：为什么不用对称/非对称加密存密码（可逆 = 拖库即泄露原文）

## 一句话

口令存储的演进是"攻击者算力增长 → 存储方提高单次成本"的军备竞赛；渐进迁移的要点是**分流验证 + 登录重哈希**，字节序等位级细节必须用真实向量取证并固化为断言。
