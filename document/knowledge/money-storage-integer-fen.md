# 知识点：金额存储——为什么用整型存分而不是浮点/DECIMAL

> 关联：M0 拍板项 B（BIGINT 分存储，park_order.amount_fen / fee_rule.unit_price_fen）
> 深度标记：金额精度是账务系统的"事故高发区"，属于一票否决级考点

## 三个候选与各自死法

**float/double（立即排除）**：IEEE 754 二进制无法精确表示 0.1——`0.1 + 0.2 != 0.3`。数据库浮点列（FLOAT/DOUBLE）与 Java double 同理。累计误差在计费放大后不可控（千万订单 × 0.001 分误差 = 账对不平）。**凡是钱，禁用浮点**是行业铁律。

**DECIMAL（精确但重）**：MySQL 的 DECIMAL 以定点十进制存储（每 9 位 4 字节），运算走定点算法，**精确但慢于整型**；Java 侧必须用 BigDecimal 对接，而 BigDecimal 有自身陷阱：
- `new BigDecimal(0.1)` 用 double 构造 → 结果是 0.1000000000000000055511151231257827...（**必须用字符串构造**）
- 除法除不尽要显式指定舍入模式（RoundingMode），否则 ArithmeticException
- 比较用 compareTo 而非 equals（equals 含精度语义，2.0 != 2.00）
- 全链路 BigDecimal 的样板代码与序列化歧义（JSON 输出字符串还是数字）

**整型存分（本项目，推荐）**：金额 = 最小货币单位整数（人民币=分）。long 精确、运算快（普通加减乘除）、无舍入陷阱、JSON/跨系统传输无精度语义歧义。换算只发生在边界：计算时全部用分，**展示层**再除 100 成元（格式化为两位小数）。

## 落地规则（不是存了 int 就完事）

1. **类型选型**：金额字段 `BIGINT`（防聚合溢出——单价×时长虽小，但统计 SUM、优惠计算会放大；int 上限 21.47 亿分=2147 万元，单笔不会超但别赌）；单价等参数列 int 够用但要评估乘积场景
2. **单位写进注释**：每个金额列注释标"单位：分"（DB 注释是活文档），Java 字段名带 `Fen` 后缀（amountFen）形成代码级约定
3. **API 单位约定**：对外 VO/接口输出"元还是分"必须在文档/字段注释固定（本项目 VO 层换算元输出时需格式化两位小数，防 2 显示成 2.0/2.00 的歧义）
4. **乘除顺序**：先乘后除防截断（`(price * minutes) / 60` 而非 `(price / 60) * minutes`）——向上取整规则用 `(durationMinutes + 59) / 60` 这类整型算术表达，不引入浮点

## 边界

- 跨境多币种场景要带币种列（本项目单币种，M0 不涉及）
- 若选 DECIMAL 也成立（银行系统常见），但整型分的**一致性成本最低**——面试重点不是"哪个绝对正确"而是"清楚每个选型的代价链"
- 涉及折扣/费率（非整数费率如 0.85 折）时，费率本身也定义为整数（如 85/100）或保留到分的定点计算——M2 优惠联动时再细化

## 一句话

金额三定律：**不用浮点、单位进注释、换算只发生在边界**；整型存分的本质是把精度问题从"运行时计算"挪到"建模时定义"。
