# 知识点/决策：设备接入传输层选型——为什么是 HTTP+HMAC+平台内 MQ，而不是 MQTT

> 关联：协议 v2（契约 §3 签名域 / §7 通道形态）、D-A（双通道降级）、D3（心跳走 HTTP 不依赖 broker）
> 用途：设备接入方案的完整性论证——"为什么不用 MQTT"是 IoT 方案被追问的第一问题，本文给出完整取舍

## 先列事实：本项目当前的传输分层

| 链路 | 承载 | 理由 |
|---|---|---|
| 事件上行 | 设备 → **RocketMQ**（gRPC）→ 平台消费；HTTP 为降级开关（`mq\|http\|dual` 零代码切换） | 事件是"至少一次"语义，走 MQ 得保序/幂等/死信的现成纵切面 |
| 心跳上行 | 设备 → **HTTP** → 平台 | 判活要有**有界时延**，不依赖 broker 存活（D3）；broker 故障时心跳+自述对账仍活 |
| 下行指令 | 平台 → **HTTP** → 设备（同步应答 + 回执码） | 同步请求应答语义最诚实：拒绝/超时/网络失败当场分清，无异步化需求 |
| 认证 | per-device HMAC 双向签名（X-Device-No + X-Device-Sign） | 与传输解耦：签名在 canonical 报文层，换承载不换认证 |

## MQTT 解决的是什么问题（先承认它的价值）

MQTT 是轻量发布订阅协议，核心能力：**长连接 + 服务端主动推送**（NAT 后设备无公网入口时，服务端仍能下发指令）、
QoS 0/1/2 投递语义、遗嘱消息（离线通知）、topic 过滤、极低带宽开销与低功耗（NB-IoT/2G 场景的事实标准）。

## 为什么本项目没有选它（按重要性排序）

1. **可达性假设不同**——MQTT 不可替代的核心场景是"设备在 NAT 后、无固定入口，需长连接收推送"。
   本项目设备与平台在专网/同网内可达（真实道闸部署在车场局域网、平台侧有网关/专线），HTTP 下行成立；
   样例的虚拟设备更是本机回环。拓扑上不缺 MQTT 的那块拼图。
2. **可靠性没有缺口**——MQTT QoS 提供的"投递保证"与业务层幂等体系（台账序守卫、按 seq 销账、超时对账）
   语义**重叠**。叠加两套可靠性语义（QoS 重投 + 业务重试）反而制造"谁为准"的复杂度；
   本项目把"可靠"收敛在平台内部（RocketMQ + 序守卫 + 对账），最后一跳保持简单可观测。
3. **认证体系不重造**——per-device HMAC 与用户体系（Spring Security sys 域）解耦、双端契约机器钉合。
   引入 MQTT 需引入 broker 层鉴权（username/password、ACL 或 mTLS），等于把设备认证再做一遍或桥接一次。
4. **运维面不加装**——MQTT broker 是又一个要运维/压测/故障演练的基础设施。样例是单机六进程形态，
   连 MQ 三进程的内存都精调过；为"技术栈好看"引入 broker 是装饰性复杂度（与选型原则相悖）。

## 若拓扑/规模翻转，迁移路径是什么（演进预案）

触发迁移的信号：①设备进入 NAT 后/窄带（NB-IoT、Cat.1）；②设备规模到万级（HTTP 短连接握手成本显性化）；
③需要服务端主动推送（OTA、配置下发、实时开闸）。

迁移形态与**零改动面**：

- 设备侧：接 MQTT 网关（EMQX 等）；网关用**桥接**把 MQTT 消息汇入现有事件通道（EMQX → RocketMQ bridge），
  下游消费链路不变；
- 消息映射：MQTT topic 承载设备号、payload 保持**协议 v2 事件 JSON 同构**、签名进 payload/property——
  设备域抽象层（DeviceChannelAuthenticator / DeviceSignature / DeviceEventForm）**不依赖传输**，全部复用；
- 下行：HTTP 指令换 MQTT 推送时，"回执 + QUERY_STATE 对账"的语义保持，只换承载；
- 幂等/序守卫/对账体系与传输解耦——**业务可靠性层零改动**。

## 一句话

传输选型服务于部署拓扑与设备能力：本项目选"设备可直达假设下的 HTTPS+HMAC + 平台内 MQ 分层"，
把复杂度放在平台侧能观测、能演练的地方；MQTT 不是被否定，而是在当前拓扑下没有被需要的理由——
一旦拓扑翻转，它是明确的、低改造成本的迁移路径。
