# 知识点：RBAC 权限模型与菜单树（sys_menu 结构与权限串粒度）

> 关联：P1 菜单注册（200-208 九行）＋Security 迁移（@PreAuthorize hasAuthority）
> 深度标记：RBAC 是管理系统的事实标准，讲清"菜单即权限点"与后端两道闸即可吃透

## 数据模型：用户-角色-菜单（权限点）

经典 RBAC 三实体两关系：user ↔ user_role ↔ role ↔ role_menu ↔ menu。**菜单表同时承担两种职责**——前端导航树节点 + 后端权限点载体：

| menu_type | 含义 | 后端鉴权 |
|---|---|---|
| 0 目录 | 导航分组（无接口对应） | 不鉴权 |
| 1 菜单 | 页面（对应一组查询接口） | 通常由按钮权限覆盖 |
| 2 按钮 | **权限点本体**（perms 列写权限串） | @PreAuthorize 逐接口匹配 |

**权限串 = 域:资源:操作**（`park:space:list`）：三段命名让权限可读、可分类、可批量授权（角色勾选时按前缀分组）。按钮行 perms 支持逗号分隔多权限（壳子样例 `sys:role:save,sys:menu:select`）——一个操作依赖多个权限点时可共享同一按钮授权。

## 树的落地：fids 冗余父链

`menu_fid`（父 id）+ `menu_fids`（父链 `0,200,201`）——**查整棵子树免递归**：`WHERE menu_fids LIKE '0,200,%'` 一条 SQL 拿到"停车管理"下全部节点；角色授权回显也直接比对本行 fids 是否全在授权集内。代价是维护纪律：改父级必须级联更新 fids（本项目菜单由 SQL 脚本管理、层级固定，无此负担）。

## 后端两道闸（本项目 Security 链路）

1. **认证闸（过滤器链）**：AuthTokenFilter 校验 token → 查用户权限串集合 → 写入 SecurityContext；`anyRequest().authenticated()` 兜底所有未放行路径
2. **授权闸（方法级）**：接口上 `@PreAuthorize("hasAuthority('park:space:list')")`——精确匹配权限串，未授权抛 AccessDeniedException → 统一异常处理 403 语义

白名单（ANON_PATHS）只放行登录/文档/健康检查——**接口默认关，显式开**，新接口忘了加注解就是 401/403 而非裸奔，这是 Security 6 相对"URL 拦截清单默认开"的核心差异（默认拒绝原则）。

## 菜单注册脚本的工程细节（本项目 02-parking.sql）

- 固定 menu_id（200-208）避开壳子存量段 → **可重复执行**（INSERT IGNORE 幂等，配合"菜单由脚本管理"的约定，禁止手改 DB）
- 时间戳用 `unix_timestamp(now())`（对齐壳子风格）
- 菜单树在角色授权前必须存在：脚本执行顺序 = 表结构 → 菜单 → （P4 起）角色授权
- 权限串与接口的映射表是"活文档"：每加一个 Controller 接口，菜单脚本与 @PreAuthorize 同步加，两者不一致 = 权限点悬空或接口裸奔

## 边界

- **超管绕过**：roleType 判定（壳子 1-开发员/2-系统管理员/其他）——超管角色跳过逐权限校验还是拥有全权限串，两种实现二选一并注释（壳子走权限串全量查询还是 roleType 短路？AuthServiceImpl.queryUserPermissions 含 roleType 分支，实现时对齐）
- 数据权限（行级，如只看自己创建的数据）与功能权限（按钮级）是两个维度——本项目 @DataFilter 已做数据权限切面（审计零注入面），讲 RBAC 时区分"能不能进"（功能）与"能看哪些行"（数据）
- 菜单膨胀治理：按钮权限粒度到"操作"，粒度更细（字段级）不通过菜单承载

## 一句话

RBAC 的工程本质是**把权限声明化**：菜单树（权限点）由脚本管理、角色-菜单关系承载授权、@PreAuthorize 精确消费权限串；后端默认拒绝 + 白名单显式放行，是权限系统不裸奔的底线。
