# 知识点：状态机在关系表上的落位（状态列 + 时间位 + 终态）

> 关联：P1 决策（park_session 0/1/2 三态 + 三个时间位）
> 深度标记：状态机是"最简单的领域模型"，能讲清表结构如何支撑迁移合法性检查

## 状态机建模的三种实现深度

1. **散落 if-else**：状态判断埋在业务代码各处，迁移合法性靠自觉——加一个状态要全文排查，必漏
2. **状态模式（GoF）**：每个状态一个类，迁移是方法调用。Java 里类爆炸，小状态机杀鸡用牛刀
3. **表驱动 + 守卫方法（本项目）**：迁移合法性集中在一个守卫（`assertCanTransition(from, to)`），非法迁移抛业务异常；状态数量少（2-4 个）时最清晰，面试也最好讲——一张"迁移矩阵"即可穷举

## 关系表如何支撑状态机：状态列 + 时间位

只有状态列（`session_state`）不够——"何时进入该状态"是审计/对账/纠纷的第一手证据。**每条迁移路径配一个时间位**：

```
进行中 ──入场──▶ （session_entry_time 写入，创建即进行中）
进行中 ──出场──▶ 已结束（session_exit_time 写入）
进行中 ──取消──▶ 已取消（session_cancel_time 写入 + cancel_reason）
```

- 三个时间位语义互斥：同一会话最多只有一个非空（终态不可再迁移），DB 层面可用 CHECK 约束兜底（MySQL 8 支持，本项目靠应用层守卫 + 测试覆盖，注释写明）
- `updatetime` 与状态时间位的关系：updatetime 是"行最近变更"，状态时间位是"特定迁移的发生时刻"——前者通用（列表排序/排查），后者语义精确（算费依据是 exit_time 不是 updatetime）

## 终态不可逆是业务正确性，不是技术限制

"已取消的会话不能再结算"如果只在 UI 层防，接口层直接调就能绕过——**守卫必须在服务层**（事务边界内），测试用例穷举非法迁移矩阵（已结束不可取消、已取消不可结算/取消、进行中不可重复出场……）。

## 枚举 vs 魔法数

- DB 列：tinyint 语义码 + 注释（0/1/2 即字典，DB 注释是活文档）
- Java 侧：**状态枚举类**（code + desc），守卫方法接收枚举而非裸 int——把"1 到底是不是已结束"从调用点消除
- 是否上字典表（sys_dictionary）：状态集合稳定且系统内部消费（非用户可配），枚举+注释足够；字典表的价值在"运营可维护的选项"（如车位区域下拉），M0 不上
- 时间字段选型备注：本项目全库 bigint 秒级 epoch（壳子风格零 datetime）——无时区歧义（存 UTC 时刻的 epoch 或本地秒？壳子存的是本地秒，展示直出；跨时区诉求出现前不做 UTC 改造，注释标"单位秒"）

## 边界

- 状态 > 5 个或迁移规则会被运营调整 → 考虑状态表/迁移配置化（本 M0 枚举即上限）
- 需要"状态历史轨迹"审计时（谁在什么时候把订单从 A 改到 B）→ 独立状态流转日志表（M2 支付域订单状态扩展时评估，当前会话只有一条迁移路径历史，无需）
- 状态码的语义注释要带 0 值说明（tinyint 默认 0 = 第一种状态，写错 DEFAULT 会把新记录静默置成错误状态）

## 一句话

表结构对状态机的支撑 = **状态列（可比较）+ 每路径时间位（可审计）+ 终态语义（注释固化）**；非法迁移的防线在服务层守卫与穷举测试，不在 UI。
